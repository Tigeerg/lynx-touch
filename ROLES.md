# Шпаргалка по ролям

Одна страница для распорядителя работ: кто есть кто, кого звать под задачу и что должно быть готово.
Подробный протокол — [`AI_WORKFLOW.md`](AI_WORKFLOW.md), стандарты — [`CLAUDE.md`](CLAUDE.md),
проверки и версии — [`VERSIONING.md`](VERSIONING.md).

## 1. Картинка

```
                        Распорядитель работ (человек)
                     приоритет, риск, финальная приёмка
                                   |
          +------------------------+-------------------------+
          |                        |                         |
  Продуктовый менеджер        Архитектор          Тестировщик и Ревьюер
    (что и зачем)             (как и где)         (независимые ворота)
                                   |
                 +-----------------+-----------------+
                 |                 |                 |
             Исполнитель     Специалист по UI    Интегратор
              (логика)          (интерфейс)       (библиотеки)

        Технолог ЧПУ (совещательная роль) --- проверяет смысл для станка
        привлекается к G1, G2, G4 и G6; не командует и не принимает
```

Главное правило: **одна задача — один владелец файла**. Свою работу не ревьюит и не принимает тот, кто её
сделал. Без доказательства (красный тест -> зелёный, скриншот, лог) работа не принята.

## 2. Кто есть кто за минуту

| Роль | Простыми словами | Что вы даёте | Что получаете | Когда звать |
|---|---|---|---|---|
| Вы, распорядитель | решаете, что важно и что принимаем | цель, приоритет, доступ к станку | карточку, записку, отчёты | всегда |
| Продуктовый менеджер | переводит боль оператора в понятную задачу | проблему или идею | карточку задачи и критерии приёмки | в начале любой работы |
| Архитектор | решает, где и как это устроить | утверждённую карточку | записку: модули, файлы, контракты, тесты | перед крупной правкой |
| Исполнитель | пишет логику и тесты | записку и границы | код, тесты, отчёт с командами | когда нужна логика |
| Специалист по UI | делает то, что видит и нажимает оператор | сценарий и экран | экран, тексты, скриншот, Qt-порт | когда меняется интерфейс |
| Интегратор | соединяет библиотеку с продуктом | задачу и библиотеку | обёртку, сборку, замер | когда нужны OCCT, Qt, QML, 3D |
| Тестировщик | проверяет, что всё работает по факту | готовую правку | лог, коды возврата, скриншот | после реализации |
| Ревьюер | ищет ошибки и нарушения правил | diff и отчёты | блокеры, замечания, долг | перед приёмкой |
| Технолог ЧПУ | смотрит, правильно ли это для станка | сценарий и риск | доменную проверку и вопросы | когда меняется смысл для станка |

## 3. Как идёт задача

1. **Идея или дефект -> Продуктовый менеджер.** Он пишет карточку: что нужно, как проверить, что не входит.
   Вы подтверждаете, что задача нужна.
2. **Карточка -> Архитектор.** Он решает, в каких модулях жить правке, какие контракты менять и какие тесты
   должны покраснеть. Вы согласуете риск и новые зависимости.
3. **Записка -> исполнители.** Логику ведёт Исполнитель, экран — UI-специалист, библиотеку — Интегратор.
   Файлы у них не пересекаются.
4. **Правка -> Тестировщик.** Он гоняет проверки и приносит `PASS`, `FAIL`, `ENV` или `UNVERIFIED`.
5. **Отчёт -> Ревьюер.** Он ищет блокеры и проверяет, что тест не слепой, а документы не забыты.
6. **Приёмка -> Продуктовый менеджер и вы.** Каждый критерий показан проверкой или скриншотом. Вы решаете:
   принято или возвращено.
7. **Фиксация -> ведущий заход.** Журнал, версии, `projects.json`, документация и коммит — вместе.

## 4. Кого звать под задачу

| Задача | Минимальный набор |
|---|---|
| Поправить подпись, кей, иконку | UI-специалист -> Тестировщик -> Ревьюер |
| Исправить логику или дефект | Исполнитель -> Тестировщик -> Ревьюер; Архитектор — если ломается граница |
| Сделать новый экран | Продуктовый менеджер -> Архитектор -> UI-специалист (+ Исполнитель для `Action`) -> Тестировщик -> Ревьюер -> Технолог ЧПУ |
| Доработать вьювер или 3D | Продуктовый менеджер -> Архитектор -> Исполнитель и/или Интегратор -> Тестировщик -> Ревьюер |
| Поменять `UI_*`, постпроцессор, тестовую УП | Продуктовый менеджер -> Архитектор -> Исполнитель + Интегратор -> Тестировщик -> Ревьюер -> Технолог ЧПУ |
| Сборка, зависимости, мост Qt/QML | Интегратор -> Тестировщик -> Ревьюер; Архитектор утверждает решение |
| Спор о границе или тупик | Архитектор + вы; при двух одинаковых блокерах — обязательно |
| Дорожная карта | Продуктовый менеджер + Архитектор + вы |

Малую задачу можно вести в одной сессии, но ворота не исчезают. Свою правку не ревьюит и не принимает тот,
кто её написал.

## 5. Кто чего не делает

| Роль | Красная линия |
|---|---|
| Продуктовый менеджер | не пишет код, не выбирает модуль, не называет причину дефекта |
| Архитектор | не пишет производственный код и не меняет критерии приёмки |
| Исполнитель | не делает UI, не строит мосты библиотек, не ослабляет тест |
| UI-специалист | не держит логику станка в компоненте, не заводит вторые тексты и иконки |
| Интегратор | не пишет сложную математику с нуля, не меняет UI, не поднимает зависимости молча |
| Тестировщик | не правит код и тесты, не оценивает архитектуру |
| Ревьюер | не переписывает код, не требует правил, которых нет в стандарте |
| Технолог ЧПУ | не пишет код и не подписывает безопасность по документу |
| Вы | не принимаете без доказательства и не пропускаете журнал, версии и документацию |

## 6. Ворота простыми словами

| Ворота | Что значит |
|---|---|
| G0. Заявка | задача понятна, проект определён, роль названа |
| G1. Готовность | карточка заполнена, критерии проверяемы, границы названы |
| G2. Решение | записка, контракты и тест-план утверждены |
| G3. Локальная зелень | красный тест был и стал зелёным |
| G4. Полная проверка | команды `VERSIONING.md` выполнены, коды возврата прочитаны |
| G5. Ревью | блокеров нет, остальной долг записан в `TODO.md` |
| G6. Приёмка | каждый критерий показан проверкой или скриншотом |
| G7. Фиксация | журнал, версии, документация и коммит — вместе |

Не перескакивать: G4 без G3 — не проверка, G5 без G4 — ревью вслепую, G7 без G6 — преждевременный коммит.

## 7. Шаблон постановки

```
Роль: ...
Проект: ...
Что нужно оператору: ...
Как проверить: ...
Не входит: ...
```

Если не знаете проект — его определит Продуктовый менеджер. Если не знаете роль — начните с него же.
Формулировку, которую нельзя проверить, лучше переспросить, чем додумать.

## 8. Если что-то пошло не так

| Что случилось | Кому |
|---|---|
| критерий нельзя проверить или задача расплывчата | Продуктовому менеджеру |
| записка не сходится с кодом | Архитектору |
| тест красный после правки | владельцу файлов |
| экран, текст, кей или Qt-порт | UI-специалисту |
| сборка, зависимость, библиотека | Интегратору |
| не хватает среды, Qt, OCCT, прав | вам |
| один и тот же блокер после двух циклов | Архитектору и вам |
| библиотека не умеет нужное | Интегратор -> Архитектор -> вам |
| спорят о границе | вам |

## 9. Словарь

* **Скил** — файл с процедурой роли или чек-листом темы; лежит в `.opencode/skills/` и загружается по id.
* **Ворота** — обязательная проверка; без неё дальше идти нельзя.
* **Красный тест** — тест, который падает до правки и доказывает, что проверка не слепая.
* **Блокер** — дефект, из-за которого панель падает или оператор видит неверное; нужен путь достижимости.
* **ENV** — проверка не выполнена из-за среды; это не «зелено».
* **Ведущий заход** — главный агент, который собирает результат, журнал и версии.
