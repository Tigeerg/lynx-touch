# LINUXCNC-BACKEND.md — адаптер к LinuxCNC

Запись работы по подключению стойки к панели: у станка появляется второй backend рядом с
симулятором. Здесь же — честный список пробелов: что контракт требует, а `stat`/HAL дать не могут,
и что с этим решено.

Термины: словарь для человека — [`ROLES.md`](../ROLES.md), раздел 9; в тексте термин расшифрован
при первом употреблении (`AI_WORKFLOW.md`, раздел 0.2).

## 1. Границы и слои

```
LinuxCNC (stat/command, HAL)
        │  сырые факты: номера joint, коды task/interp, таблица инструмента, список сообщений
        ▼
LinuxCncLink        — интерфейс (backend/linuxcnc_link.h), без типов контракта
        │
LinuxCncBackend     — отображение в контракт (backend/linuxcnc_backend.cpp), проверяется тестами
        │
BackendBridge.qml   — шов панели
        │
экраны (main.qml и компоненты)
```

Почему так: адаптер к библиотеке — самая рискованная часть, а библиотеки на машине разработчика
нет. Поэтому отображение отделено от вызова библиотеки: **отображение написано и проверено здесь**
(13 тестов на подставной связи), а **вызов библиотеки пишется на стойке** по карточке в
`backend/linuxcnc_nml_link.cpp`, где перечислено, какое поле `stat` куда идёт.

## 2. Сборка

* LinuxCNC подключается опцией CMake: `-DLYNX_WITH_LINUXCNC=ON` (по умолчанию `OFF`). С ней
  собирается реальный линк и линкуются библиотеки стойки; без неё собираются адаптер и его тесты.
* `--backend=linuxcnc` без линка завершает запуск с понятным сообщением и кодом 1 **без тихого
  отката на симулятор**: панель на станке не должна показывать выдуманные числа.
* Проверка адаптера входит в `scripts/check-qt-panel.ps1`: `lynx-linuxcnc-test` (13 случаев) и
  `lynx-backend-test` (16 случаев) идут вместе с QML-тестами (37).

## 3. Отображение (уже сделано и проверено)

| Панель (контракт) | LinuxCNC | Правило |
|---|---|---|
| `run` | `stat.estop`, `stat.task_state`, `stat.interp_state` | `ESTOP` → `ALARM` (`task_state = ERROR`) → `HOLD` (`interp_state = PAUSED`) → `RUN` (`task_state = EXEC`) → иначе `IDLE` |
| `mode` | `stat.task_mode` | `auto` → `AUTO`, `mdi` → `MDI`, `manual` → `JOG` (режима `MPG` у станка нет — это шаг панели) |
| `position` | `stat.joint_position` минус активное `stat.g5x_offset` | рабочая позиция (DRO) |
| `machinePosition` | `stat.joint_position` | машинная позиция |
| `offsets` | `stat.g5x_offset[0..5]` | строки G54…G59, активная — `stat.g5x_index` |
| `tools` | `stat.tool_table[]`, `stat.tool_in_spindle` | номер, имя, диаметр, длина; ресурс — см. пробел 3 |
| `overrides` | `stat.feedrate`, `stat.spindle_scale`, `stat.rapid_scale` | проценты; ряд быстрых 5/25/50/100 |
| `singleBlock`, `optStop`, `dryRun` | `stat.single_block`, `stat.optional_stop`, флаг холостого хода | уточнить на стойке |
| `program` | `stat.file`, строки файла, `stat.motion_line`, `stat.current_line` | активная УП и кадр |
| `alarms` | канал сообщений оператора | «код текст» разбирается, уровень — см. пробел 4 |
| `clock` | системные часы | часы смены, как в React |
| команды | `command.task_*`, `task_mode`, `jog`, `mdi`, `program_open`, `override`, таблица инструмента, `g5x` | отказ станка возвращается строкой |

## 4. Пробелы: что контракт требует, а станок не даёт

Панель (React) держит эти понятия сама; в контракт они попали из неё, а не из станка. Решение по
каждому — «где брать»; до реализации в адаптере стоит честная заглушка.

1. **Рабочее место `SETUP`/`TEST`/`RUN`.** У LinuxCNC такого состояния нет: это навигация панели.
   *Решение:* остаётся состоянием панели; адаптер возвращает пусто (`workplace()` → `""`), а
   `setWorkplace()` принимает вызов и не трогает станок. На стойке рабочее место может
   разворачиваться в режим (`manual`/`auto`) и холостой ход.
2. **Каталог УП: список файлов и дата.** `stat` знает одну открытую УП.
   *Решение:* отдельное хранилище (как настройки), а не `stat`; адаптер отдаёт одну строку — файл
   контроллера. `loadProgram(1..n)` отказывает.
3. **Ресурс инструмента и время резания инструментом.** В `stat` их нет.
   *Решение:* `setToolLife` отказывает («не хранится в LinuxCNC»), `tools[].life` = 100, `toolTime`
   пуст. На стойке — отдельный учёт (файл/HAL), тогда поле заполняется.
4. **Уровень сообщения (`авария`/`предупреждение`/`инфо`).** Канал сообщений уровня не несёт.
   *Решение:* адаптер ставит `info`; разбор по диапазонам кодов — когда стойка подтвердит таблицу.
5. **Результат щупа.** `stat` не знает результата; щуп гоняет программа или мастер панели.
   *Решение:* результат от мастера или с HAL-пина; до этого — пусто.
6. **Нагрузка шпинделя и осей.** Это HAL-пины (`spindle.N.load` и т. п.), не `stat`.
   *Решение:* линк читает пины через HAL-доступ; до этого `load()` = 0, `axisLoad` — нули.
7. **Счётчик цикла и готовых деталей.** В `stat` нет.
   *Решение:* цикл панель может считать сама по состоянию `RUN`; счётчик деталей — панель/программа.
   `countPart()` сейчас отказывает; после решения — либо HAL-таймер, либо счёт панели.
8. **«Старт с кадра» (run from line).** Нужна команда интерпретатора «выполнять с строки».
   *Решение:* сегодня адаптер отображает её в обычный ПУСК и это помечено; на стойке — настоящее
   run-from-line.
9. **`toolTime`, `probe.step`, архив сообщений.** Мелочи того же рода: берутся из панели или HAL.

Общее правило: **адаптер ничего не выдумывает.** Где станок не даёт числа — отказ с причиной или
пустое значение, а не правдоподобная цифра.

## 5. Карточка для стойки

1. Собрать с `-DLYNX_WITH_LINUXCNC=ON`, подключив заголовки и библиотеки LinuxCNC (stat/command,
   NML) в `CMakeLists.txt`.
2. Написать `LinuxCncNmlLink` в `backend/linuxcnc_nml_link.cpp` по списку в комментарии файла:
   поля `stat` → методы линка, команды → `command`. Отображение трогать не нужно — оно уже
   покрыто тестами, менять его следует только вместе с тестом.
3. Прогнать `scripts/check-qt-panel.ps1` (адаптер и панель) и `--backend=linuxcnc` на стойке.
4. Приёмка: панель показывает **реальные** координаты, режим, УП, коррекции и сообщения;
   ПУСК/ПАУЗА/СБРОС/АВАРИЯ и коррекции доходят до станка; отказ станка виден строкой.
5. Заполнить пробелы 1–9 по одному, каждый с тестом на подставной связи и записью в
   `CHANGELOG.md`.
