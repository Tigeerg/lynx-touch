# PLAN-QUICKPROG.md — быстрое программирование УП в стойке

Черновик к этапу M5 дорожной карты. Источник истины о поведении — код и его прогон; здесь замысел,
границы, формы ввода и порядок работ. Английское зеркало — [PLAN-QUICKPROG.en.md](PLAN-QUICKPROG.en.md).

## 1. Что делаем и чего не делаем

**Цель.** Оператор без CAM и без ручного набора G-кода создаёт короткую УП на стойке: выбирает операцию,
вводит размеры, видит траекторию и сохраняет `.ngc` для запуска.

**Границы первой версии:**

* 3-осевой фрезерный станок, миллиметры, `G54`..`G59`, абсолютные координаты;
* простые операции: торцевание, прямоугольный и круглый карман, сверление и сетка отверстий;
* плоский G-код без O-подпрограмм: его понимает существующий вьювер и его можно прочитать глазами;
* модель программы хранится отдельно от `.ngc`, чтобы операцию можно было открыть и поправить;
* запуск — только после предпросмотра и проверки коллизий; автоматического пуска нет.

**Не входит:** полноценный CAM, STEP/DXF-импорт, 3D-поверхности, адаптивная обработка, острова и остаточная
обработка, токарные циклы, автоматическое распознавание элементов, свои постпроцессоры.

**Стратегия.** Первый вертикальный срез — прямоугольный карман целиком: форма -> `CamPath` -> `emit` ->
2D-предпросмотр -> файл -> тесты. Он доказывает конвейер, не размазывая риск по четырём операциям. В том же
этапе добавляются торцевание, сверление и список операций; документ с самого начала хранит массив операций,
даже если первая форма создаёт одну. Многооперационная программа не откладывается «на потом»: без неё
быстрое программирование не решает задачу детали.

## 2. Что нужно оператору

Порядок — по частоте и пользе для короткой программы на стойке.

| Операция | Зачем оператору | Версия | Сложность |
|---|---|---|---|
| Торцевание плоскости | снять верх, выровнять заготовку | MVP | S |
| Прямоугольный карман | самая частая фрезерная операция | MVP | M |
| Круглый карман | отверстие под палец, стакан, бобышку | MVP | M |
| Сверление: одно, сетка, круг | отверстия по чертежу | MVP | S-M |
| Контур: замкнутый/открытый | обработка наружного или внутреннего профиля | P1 | M |
| Паз | шпоночный паз, канал | P1 | M |
| Резьба метчиком | `G84`, если станок умеет жёсткое нарезание | P1 | M |
| Фаска/снятие кромки | убрать заусенец после контура | P1 | M |
| Массив, поворот, группа операций | несколько одинаковых элементов по чертежу | P1 | M |
| Произвольный G-код отдельным блоком | выход для нестандартной операции | P1 | S |
| Цековка, резьбовая фреза, гравировка | крепёж, резьба, маркировка | P2 | M |
| Блок щупа в программе | обмер между операциями | P1 | M |
| Карман с островом, остаточная обработка | сложные детали | P2 | L |
| DXF/STEP-импорт | перенос геометрии с чертежа | P2 | L |

MVP без контура — сознательное решение: контур требует подводов, отводов и коррекции на радиус, а это
главный источник зарезов. Сначала проверяем карманы, торцевание и сверление на реальной детали.
MVP начинается с кармана end-to-end; остальные операции добавляются сразу после него, а не отдельными
полуфабрикатами.

## 3. Как это устроено в промышленных стойках

Смотрел не на рекламу, а на повторяющиеся приёмы.

| Стойка | Что делает | Что берём |
|---|---|---|
| **Fanuc Manual Guide i** | циклы обработки, «fixed form sentences» для повторяемых блоков (смена инструмента, СОЖ), фигура как подпрограмма для черновой/чистовой | готовые заготовки программы, повторяемая преамбула, графическая проверка |
| **Siemens ShopMill/ShopTurn** | редактор шагов обработки, отдельный калькулятор контура до 256 элементов, карман/остров, черновая и чистовая, симуляция | список операций, геометрия отдельно от обработки, черновая/чистовая как разные проходы |
| **Heidenhain TNC** | формы с графикой, поясняющей каждый параметр; циклы карманов, бобышек, пазов; Klartext | подсказка-картинка у каждого поля, крупные формы, циклы |
| **Haas VPS/IPS** | визуальные шаблоны, стандартные циклы `G150`, `G12/G13`, графика | визуальный выбор операции и понятные шаблоны |
| **Mazak Mazatrol** | единицы программы: заготовка, инструмент, форма, обработка; автоматический подвод/отвод | сначала заготовка и инструмент, потом операции; модель единиц, а не строк G-кода |
| **Hurco WinMax** | блоки данных, вкладки Roughing/Rest/Finishing, `AutoCalc`, шаблоны, повтор, DXF | блоки, вкладки, автоподстановка размеров, повтор операций |
| **Okuma AOT-IGF** | пошаговый ввод с интерактивной графикой и проверкой | пошаговый мастер и графика |
| **Tormach PathPilot** | conversational-программирование на LinuxCNC: сверление, резьба, карманы, перестановка операций | ближайшая к нам архитектура: операции -> G-код, без полного CAM |
| **NativeCAM** | отдельный add-on для LinuxCNC: каталог фигур, полилиния, массивы/повороты, сверление, цековка, резьбовая фреза, гравировка, щуп, произвольный G-код | каталог операций, группы и массивы, `Custom G Code`, блоки щупа, порядок проекта |
| **LinuxCNC NGCGUI/PyNGCGUI** | формы по параметрам подпрограмм, `Create Feature`, `Finalize`, склейка нескольких операций, предпросмотр | параметры с метками и умолчаниями, список фич, склейка, предпросмотр |

Общий вывод: у всех есть **заготовка и инструмент до операций**, **список операций**, **форма с
графикой**, **предпросмотр** и **сохранение в G-код**. Никто не заставляет оператора начинать с чистого
редактора G-кода.

## 4. Что взять из LinuxCNC

### 4.1 NGCGUI/PyNGCGUI

Официальный документ LinuxCNC описывает NGCGUI как Tcl-приложение, а PyNGCGUI — как его Python-версию:
каждая подпрограмма `.ngc` даёт вкладку, параметры `#1`..`#30` превращаются в поля, специальные комментарии
задают метку и значение по умолчанию, кнопка `Create Feature` добавляет операцию, `Finalize` склеивает
несколько операций в один файл, рядом можно положить картинку-подсказку.

Что берём:

* **схему «операция = параметры + форма + подсказка»**;
* **список фич и их порядок**;
* **умолчания и метки** у каждого поля;
* **предпросмотр до сохранения**;
* **склейку операций в один файл**.

Чего не берём:

* Tcl/Python-код и зависимость от `PyNGCGUI`: в проекте Python запрещён, а GPL-код LinuxCNC нельзя
  копировать в Apache-2.0-проект;
* O-подпрограммы в первой версии: вьювер и оператор должны видеть плоский G-код;
* ручное редактирование подпрограмм как основной путь.

### 4.2 QtPlasmaC

В QtPlasmaC есть «Conversational Shape Library»: выбор материала, параметры фигуры, предпросмотр. Для
фрезеровки это не готовое решение, но приём полезен: **режимы резания берутся из материала и инструмента,
а не вводятся с нуля каждый раз**.

### 4.3 NativeCAM

NativeCAM — отдельный add-on для LinuxCNC, а не часть его ядра. Он встраивается в AXIS или gmoccapy,
распространяется под GPL-2.0, написан на Python/GTK; есть порт 2.0b на Python 3/GTK3. Каталог операций
показывает, что реально нужно оператору:

* **Basic Shapes:** прямоугольник, круг, круг по двум точкам, паз/овал, радиальный паз, эллипс,
  многоугольник, чистовая обработка поверхности;
* **Advanced:** полилиния из линий и дуг, зеркало, повтор элементов, цековка под винт с цилиндрической
  головкой, резьбовая фреза, гравировка TrueType, круг со шпоночным пазом;
* **Drilling:** одно отверстие, массив, правильная и неправильная окружность отверстий;
* **Groups:** группа операций, смещение/поворот, радиальный и прямоугольный массив, индекс оси A;
* **Tool Change:** концевая фреза, сверло/развёртка, резьбовая фреза;
* **Probing:** края, куб/цилиндр, массив точек, поверхность, отверстие;
* **Miscellaneous:** заготовка, произвольный G-код, вставка файла G-кода, комментарий, заметки проекта.

Что берём:

* **каталог операций, разделённый на простые и продвинутые** — оператор не тонет в списке;
* **группы, массивы и поворот** — это не «экзотика», а частая работа по чертежу;
* **явный блок смены инструмента и блок щупа**;
* **`Custom G Code` как выход**, а не как основной способ;
* **проект как упорядоченный список**, а не одна огромная форма.

Чего не берём:

* Python/GTK и GPL-код NativeCAM: проект на TypeScript/QML/C++, лицензия Apache-2.0;
* «real-time CAM» и скрытые автоматические решения;
* полный набор операций сразу: NativeCAM — эталон объёма, а не обязательство первой версии.

Важный урок из обсуждений NativeCAM: неявные операции могут дать формально верный, но неожиданный результат.
Поэтому у нас каждая операция показывает **явную траекторию, глубину, инструмент и предупреждения**, а
`Custom G Code` отделён от мастеров и требует подтверждения.

## 5. Сценарий оператора

1. **Вход.** На экране «Работа» — «Новая быстрая программа» или «Открыть быструю программу».
2. **Заготовка.** Оператор подтверждает `G54`, габарит заготовки, `Z` верха, безопасный `Z`, единицы (мм).
   Значения подставляются из текущего состояния; можно взять с DRO.
3. **Инструмент.** Выбор из существующей таблицы инструмента: диаметр, тип, вылет. Режимы (об/мин, подача,
   врезание) подставляются из материала и диаметра, но остаются редактируемыми.
4. **Список операций.** Пустой список и крупная кнопка «Добавить операцию». Уже добавленные — карточками:
   тип, инструмент, габарит, глубина, предупреждения.
5. **Выбор операции.** Плитки с текстом и значком: «Плоскость», «Карман», «Круглый карман», «Отверстия».
   Не только иконки: на P1 подпись обязательна.
6. **Форма операции.** Слева — поля, справа — живой предпросмотр. Вкладки: «Геометрия», «Инструмент»,
   «Режимы», «Подвод/отвод». У полей — подсказка-картинка и единица. Кнопка «Взять с DRO» для центра и
   верха. Ошибки показываются рядом с полем, а не одной строкой внизу.
7. **Добавление.** «Добавить в программу» активна только при валидной операции. Причина отказа — в подсказке.
8. **Программа.** Карточки можно менять местами, дублировать, отключать и удалять. Смена инструмента
   группируется; между группами — безопасный отвод.
9. **Проверка.** «Проверить» строит траекторию, показывает заготовку, оценивает время, ищет коллизии
   простой проверкой вьювера. Ошибки блокируют сохранение.
10. **Сохранение.** Два файла: `.qprog` — модель для правки, `.ngc` — готовая УП. В шапке `.ngc` —
    пометка «generated», имя программы и версия генератора.
11. **Запуск.** «Открыть в редакторе» или «Запустить». Пуск — только после предпросмотра и без ESTOP,
    по тем же `guards.ts`, что и обычная программа.

### 5.1 Три конфигурации панели

* **P1, только клавиши:** фокус по полям, `F`-клавиши для «Добавить», «Проверить», «Сохранить»; ввод с
  цифрового блока; никаких жестов.
* **P2, клавиши + сенсор:** те же действия касанием; крупные цели; поворот 3D не мешает форме.
* **P3, только сенсор:** экранная клавиатура и цифровой блок; пошаговый мастер; подписи, а не `F`-клавиши.

## 6. Модель данных

Документ программы — не состояние станка. Его можно хранить отдельно от `machine.ts` и подключать к машине
только командами «загрузить УП», «проверить», «запустить».

```ts
// Документ, который сохраняется в .qprog и открывается снова.
type QuickProgram = {
  schema: 1
  name: string
  units: 'mm'
  wcs: 'G54' | 'G55' | 'G56' | 'G57' | 'G58' | 'G59'
  stock: StockBox
  safeZ: number
  operations: QuickOperation[]
}

type QuickOperation =
  | FaceOperation
  | RectPocketOperation
  | CirclePocketOperation
  | DrillOperation
  | ContourOperation   // P1
  | SlotOperation      // P1
  | TapOperation       // P1

// Временная форма ввода: строки, курсор, ошибка; не MachineState.
type CamForm = {
  op: QuickOperation['kind']
  values: Record<string, string>
  cursor: number
  preview: CamPath | null
  error: { field: string; reason: string } | null
  writeName: string | null
}

// Результат планировщика: ходы, а не строки УП.
type CamMove = {
  kind: 'rapid' | 'cut'
  to: { x: number; y: number; z: number }
  feedMmMin?: number | null
  arc?: { cw: boolean; i: number; j: number }
}

type CamPath = {
  moves: CamMove[]
  bboxMm: { xMin: number; xMax: number; yMin: number; yMax: number; zMax: number }
  estMm: number
  uuid: string
}
```

Общие поля операции: `id`, `kind`, `enabled`, `tool`, `spindleRpm`, `feed`, `plungeFeed`, `coolant`,
`topZ`, `depth`, `stepDown`, `finishAllowance`, `notes`. Геометрия — именованные типы (`Point`, `Rect`,
`Circle`, `Polyline`), не кортежи. `CamForm` живёт вне `MachineState`, но читает `isBusy(s)`; при
`CAM_ACCEPT` строки формы переводятся в нормализованную `QuickOperation`, при `CAM_CANCEL` не остаётся ни
предпросмотра, ни файла.

## 7. Архитектура

Чистая логика — в `apps/react-interface/lib/cnc/cam/`, без JSX и DOM:

| Модуль | Ответственность |
|---|---|
| `ops.ts` | `QuickProgram`, операции, `CamForm`, `CamPath`, `CamMove`, `CamContext` |
| `defaults.ts` | умолчания по инструменту и материалу |
| `validate.ts` | guard clauses и типизированный `{ ok } \| { bad: { field, reason } }` |
| `toolpath.ts` | планировщик: `CamPath` из операции, без строк УП |
| `feeds.ts` | режимы через существующие `calc.ts`/`spindle.ts`, не вторая формула |
| `face.ts`, `pocket-rect.ts`, `pocket-circle.ts`, `drill.ts` | операции MVP |
| `contour.ts`, `slot.ts`, `tap.ts` | P1-операции |
| `planner.ts` | порядок операций, смена инструмента, безопасный отвод |
| `emit.ts` | плоский G-код, шапка, `UI_*`, финал |
| `serialize.ts` | `.qprog` и проверка схемы |
| `cam.ts` | действия `CAM_OPEN`, `CAM_OP`, `CAM_PARAM`, `CAM_ACCEPT`, `CAM_CANCEL`, `CAM_PREVIEW`, `CAM_WRITE`; вне `MachineState`, но с `isBusy(s)` |

Планировщик возвращает `CamPath`, а не строку; `emit.ts` печатает G-код, предпросмотр рисует те же ходы.
Один источник геометрии — два представления. `CAM_WRITE` — единственная точка записи; запись идёт через
`files.ts`, а не через новую файловую систему. `parseWords` проверяет синтаксис, но не заменяет геометрию и
вьювер.

UI — в `components/cnc/cam/`: `cam-screen`, `operation-picker`, `cam-form`, `operation-list`,
`cam-preview`. Экран получает `QuickProgram` и `dispatch`, как остальные экраны. Первая версия формы может
создавать одну операцию, но модель и экран списка проектируются под массив с первого дня.

### 7.1 G-код

Шапка: `G21 G90 G94 G17 G40 G49 G80`, `G54`, безопасный `Z`, `T`/`M6`, `S`/`M3`, `M8`.
Для вьювера — `UI_STOCK`, `UI_OP`, `UI_TOOL` теми же комментариями, что и в обычной УП.
Финал: `M9`, `M5`, `G0 Z<safe>`, `M30`.

В MVP — центр траектории, без `G41/G42`: коррекция на радиус и подводы — отдельный этап, иначе зарез.
Сверление — `G81`/`G83`; `G84` — P1 и только если станок подтверждает жёсткое нарезание. Дуги — `G2/G3`
с `I/J`, полная окружность — двумя полудугами или `I/J` без конечной точки (проверить на вьювере).

## 7.3 Готовность к станку (второй заход демо)

Первый заход доказал конвейер и получил от технолога список того, чего не хватает годной УП. Второй заход
закрывает постпроцессорную часть — без неё демо остаётся витриной. Образец того, как это делает существующий
постпроцессор: `data/cad-testdata/Test_model.ngc` (строки N20, N55, N145, N155, N180).

**Что добавляем (решение):**

| Чего не хватало | Как решаем | Где |
|---|---|---|
| Коррекция длины `G43` | у инструмента появляется номер коррекции `hNumber` (по умолчанию равен номеру инструмента); после `T.. M6` идёт `G43 Z<safe> H<n>` — так же, как `N55 G43 Z15. H2` в образце | `core/ops.h` (`ToolRef`), `core/emit.cpp`, `.qprog` (`op.h`), `--help` (`--h`) |
| Смена инструмента не на парковке | перед каждым `M6` (и в начале программы) — `G53 G0 Z0`, как `N20 G53 G0 Z0` в образце: станок уходит в машинный ноль, а не в безопасную высоту детали | `core/emit*` |
| Нет остановки между операциями | `M1` перед каждой операцией, начиная со второй: оператор осматривает канал/снимает стружку; включение — поле `stopAfterOp` документа и `--stop` (по умолчанию включено), в `.qprog` `stopAfterOp on` | `Program`, `emit` |
| Нет сглаживания | `G64 P<допуск> Q<допуск>` в шапке после смещения, допуски — поля программы (`g64P`, `g64Q`, по умолчанию 0.01 мм, как `N180 G64 P0.01 Q0.01`), меняются `.qprog` и `--g64` | `Program`, `emit_frame` |
| Шаг растра кармана зашит | шаг — поле каждой кармана-операции (`stepOverPct`, по умолчанию 70 %), в `.qprog` (`op.stepOver`), в `--help` (`--step-over`); у прямоугольного берётся ещё и при чистовом проходе по стенке | `RectPocketOp`, `CirclePocketOp`, `path_pocket*` |
| Режимы сверления «на глаз» | таблица по материалам для сверла (HSS и твёрдый сплав отдельными строками), как у фрезы; строка-источник печатает и материал, и тип сверла | `core/feeds` |

**Порядок блоков операции после правки** (совпадает с образцом):

```
(UI_TOOL: T=.. TYPE=.. D=..)
G53 G0 Z0            только при смене инструмента и в начале программы
T.. M6
G43 Z<safe> H<n>
S.. M3
M8
<ходы операции>
M9 M5
G53 G0 Z0            в конце программы
M30
```

`M1` ставится перед `UI_OP` следующей операции (после `M9/M5` предыдущей) — оператор видит паузу на границе
операций, а не внутри.

**Границы.** Номер коррекции — это номер в таблице коррекций стойки; демо его не проверяет, оператор задаёт
сам (по умолчанию равен номеру инструмента). Реальной работы `G43` (вылет, датчик) демо не делает: строка
печатается, станок берёт число из своей таблицы. `G64` — допуск, не скорость; его значение проверяет
технолог на станке.

**Приёмка.** В `.ngc` есть `G43 H` после каждой смены инструмента, `G53 G0 Z0` перед каждой сменой и в финале,
`M1` перед каждой операцией кроме первой, `G64` в шапке; шаг растра меняется из `.qprog` и виден в сводке;
сверление берёт строку из таблицы с источником. Всё это держат проверки, а не глаза: каждый элемент —
отдельный случай в `quickprog_check`, плюс round-trip через парсер вьювера не должен ломаться на `G53`/`G43`/
`M1`/`G64`.

## 7.4 Перенос конвейера в панель (P1, первый срез)

Демо доказало конвейер и довело его до готовности к станку на C++. Панель — это React/TypeScript, поэтому
логику переносим **по контракту, а не копированием кода**: те же типы, те же правила, те же проверки в каждой
операции, тот же формат `.qprog`.

**Что переносим и куда (`apps/react-interface/lib/cnc/cam/`, без JSX и DOM):**

| Модуль панели | Что берёт из демо | Отличие |
|---|---|---|
| `ops.ts` | `QuickProgram`, `Operation`, `CamPath`, `CamMove`, типы геометрии (`Point3`, `Rect`, `Circle`) | `Operation` — размеченное объединение (`kind`), как `QuickOperation` из §6: так форма и reducer проверяются типом, а не полем |
| `feeds.ts` | таблицы фрезы и сверла, формулы, строка источника | числа **не дублируются из C++**, а живут здесь; `calc.ts` остаётся калькулятором, `feeds.ts` стоит на его формулах. Демо и панель должны давать одну строку режимов — это проверяется сверкой в тестах, а не глазами |
| `validate.ts` | правила §8 как `{ field, reason }` | причина показывается у поля формы, а не строкой внизу |
| `path.ts` | планировщики: торцевание, карманы, сверление | возвращает `CamPath` (ходы), не строки УП |
| `emit.ts` | шапка, теги `UI_*`, `G43`, `G53`, `M1`, `G64`, финал | вывод — массив строк для `setLines`, а не файл |
| `serialize.ts` | `.qprog` схема 1 | читается файлом демо и наоборот: формат общий |
| `cam.ts` | подсистема: `CAM_*` действия | живёт **вне** `MachineState`, как `CamForm` §6; читает `isBusy(s)` |

**Встраивание в панель (решения):**

1. **Экран.** Новая вкладка панели не заводится: по раскадровке 1024x600 вкладок пять, шестая сломает софт-кеи
   и сенсорную сетку. Экран быстрого программирования — **оверлей на экране «Программа»**, открывается
   софт-кеем `F4` («Быстрая УП»), закрывается `F4`/`ESC`. В оверлее три колонки: слева список операций,
   в центре форма операции, справа предпросмотр 2D (он же даёт `buildToolpath` из `toolpath.ts` по
   сгенерированным строкам — один источник геометрии).
2. **Состояние.** `CamState` — отдельная ветка `MachineState` (`cam: CamState | null`), а не второй reducer:
   действия `CAM_OPEN`, `CAM_CLOSE`, `CAM_OP` (выбор вида), `CAM_PARAM` (правка поля), `CAM_ACCEPT`
   (добавить операцию), `CAM_CANCEL`, `CAM_PREVIEW`, `CAM_SAVE` идут через реестр подсистем, как остальные.
   `CamForm` (строки полей, курсор, ошибка) — часть `CamState`.
3. **Запись.** `CAM_SAVE` — единственная точка записи, идёт через `files.ts` (`setLines`), то есть оператор
   получает УП в списке файлов панели и может сразу открыть её в редакторе. Отдельного файлового API не
   заводим.
4. **Защита.** `CAM_SAVE` запрещён при `ESTOP` и во время прогона (`isBusy(s)`), как `CAM_WRITE` §8.
5. **Клавиши.** `F1..F3`, `F5..F8` в оверлее остаются за операциями панели; в оверлее работают `F4` (закрыть),
   `ESC`, стрелки/`Enter` по полям и цифровой ввод. Сенсор работает касанием (`P2`/`P3`), панельный (`P1`) —
   только клавишами; это проверяется на трёх конфигурациях.

**Порядок срезов переноса (каждый — отдельный коммит с проверками):**

| Срез | Что |
|---|---|
| C1 | типы, режимы и проверки (`ops`, `feeds`, `validate`) + тесты, сверка чисел режимов с демо |
| C2 | планировщики и вывод УП (`path`, `emit`) + тесты против эталонных `.ngc` демо |
| C3 | `.qprog` (`serialize`) и взаимная читаемость файла демо и панели |
| C4 | подсистема `cam.ts` в реестре действий + тесты на `isBusy`, `CAM_SAVE` через `setLines`, отмену |
| C5 | оверлей на экране «Программа»: список, форма, предпросмотр, `F4`/`ESC`, сенсор |

**Приёмка P1-первого среза.** Оператор на панели 1024x600 создаёт программу из трёх операций (торцевание,
карман, сверление), видит предупреждения у полей, сохраняет УП и получает её в списке файлов; получившийся
`.ngc` совпадает по геометрии с файлом демо для тех же параметров; панельный и сенсорный варианты проходят
проверку вручную (скриншот по `panel-ui`). Вьювер читает сохранённую УП (`gcodeviewer --smoke`).

## 7.5 Q3: проверка вьювером, коллизии, замена файла, debounce

Четвёртый заход закрывает то, что план (§5 п.9-10, §8, §10, §11) требует перед пуском на станок.

| Что | Решение | Где |
|---|---|---|
| **Вьювер не проверяет сохранённую УП** | проверка `viewer.geometry`: для программы из нескольких операций строится УП, кладётся в `apps/react-interface/testdata/viewer/` (эталоны демо), и тест сверяет её с парсером вьювера (`gv::parseGcode`, `seg_count > 0`, число этапов, подписи `UI_OP`, `UI_TOOL`); живой запуск `gcodeviewer --smoke` — ручной шаг оператора, его результат пишется в приёмку | `lib/cnc/cam/viewer-check*` + тест |
| **Коллизия не определена** | в панели — **своя простая проверка** без вьювера: для каждой точки траектории инструмент (диск радиуса `D/2`) должен быть внутри габарита заготовки плюс допуск; выход за заготовку в плане = предупреждение, срез ниже дна заготовки = ошибка; имя проверки явное, в отчёте написано `UNVERIFIED` для реальной геометрии деталей | `lib/cnc/cam/collision.ts` |
| **Сохранение не блокируется проверкой** | `CAM_SAVE` спрашивает `checkProgram`; ошибки блокируют запись (сообщение с полем), предупреждения показываются в шапке оверлея и пишутся в комментарий УП `(QUICKPROG WARNING: …)` | `cam.ts`, `emit*.ts` |
| **Замена файла молча** | `CAM_SAVE` при совпадении имени просит подтверждение: первое нажатие ставит `pendingSave`, второе в течение 5 секунд пишет и делает резервную копию старого содержимого в файл `<имя>.bak` (в панели — файл `ИМЯ.bak` в списке файлов) | `cam.ts`, `files.ts` |
| **Debounce предпросмотра** | правка поля пересчитывает предпросмотр через 150 мс после последней правки; поле хранит набранный текст сразу, предпросмотр — отложенный; в `CamState` поле `previewAt` (момент последнего пересчёта) и `pending` (есть ли правки без пересчёта). В тестах время подставляется, а не измеряется | `cam.ts` |
| **`.qprog` на диск** | `CAM_SAVE` пишет два файла: `.ngc` и `.qprog` (модель), второй с тем же именем и расширением, чтобы программу можно было открыть (позже — с диска); текст `.qprog` — `serializeProgram` | `cam.ts` |
| **Три конфигурации** | `cam-softkey`/`keys-route` тесты на P1 (клавиши), P2 (клавиши+сенсор), P3 (сенсор): в P1 нет касательных путей, в P2 и P3 все действия оверлея доступны | тесты |

**Приёмка Q3.** Программа с ошибкой (инструмент больше кармана) не сохраняется; программа с предупреждением
(выход за заготовку в плане) сохраняется и несёт предупреждение в УП; замена файла требует двух нажатий и
делает `.bak`; правка поля не пересчитывает предпросмотр чаще раза в 150 мс; сохранение даёт и `.ngc`, и
`.qprog`; сохранённая УП читается парсером вьювера (сегменты, этапы), живой `gcodeviewer --smoke` — шаг
ручной приёмки.

## 7.6 Q4 и Q5: новые операции

Пятый и шестой заходы расширяют набор операций до заявленного в §2. Правило переноса то же, что в 7.4:
логика в `lib/cnc/cam/`, форма в `components/cnc/cam/`, `.qprog` и демо читают одно и то же, эталоны — из
демо. Каждая операция проходит один и тот же путь: тип в `ops.ts`, поля в `cam-fields.ts`, планировщик
`path-<вид>.ts`, правило в `validate-<вид>.ts`, вывод в `emit.ts`, `.qprog`, тесты на числа и границы.

**Q4 (P1).** Операции, которые план считает нужными для реальной детали, кроме карманов и сверления.

| Операция | Что делает | Главный риск и решение |
|---|---|---|
| **Контур** (замкнутый и открытый) | фрезеровка по профилю: полилиния из точек `Point3` в плоскости XY, направление (по/против часовой), число проходов по Z, припуск | коррекция на радиус: **MVP контура — без `G41/G42`**, траектория — центр фрезы, смещённый по нормали профиля на `D/2` в сторону материала; нормаль считается по сегментам, на стыках — биссектриса. Зарез на вогнутом угле меньше радиуса фрезы — **ошибка валидации** «угол острее фрезы» |
| **Паз** | прямая канавка: две точки, ширина, глубина, проходы | ширина меньше диаметра — ошибка; ширина больше двух диаметров — предупреждение «лучше контуром»; врезание — по часовой стрелке на каждом проходе для прорезания паза шире фрезы |
| **Метчик** | резьба `G84` | только если станок подтверждает жёсткое нарезание; параметр станка `rigid_tapping` в настройках панели, по умолчанию **выключен**; при выключенном — ошибка валидации с текстом про жёсткое нарезание |
| **Фаска** | снятие кромки по профилю: `chamferMm` | фаска больше `D/2` — ошибка; в MVP — только прямые участки, дуги фаски — предупреждение |
| **Массив и поворот** | копии операции по сетке и вокруг точки | копии **разворачиваются в плоский список** при `CAM_ACCEPT`, отдельного вида в `.qprog` нет: проще проверять, проще печатать; ограничение — 100 копий |
| **`Custom G Code`** | блок произвольного G-кода | отдельный вид, **не проверяется геометрически**, но проходит проверку парсера вьювера (`viewerIssues`); в списке помечен предупреждением «проверьте вручную» |
| **Блок щупа** | обмер между операциями (`G38.2`/`G31` по выбору станка) | в MVP — только щуп `T… ф…` из таблицы и `M6`; сама логика обмера — P1-позже, здесь диапазон и скорость касания |

**Q5 (P2).** Операции, которые делают систему пригодной для сложных деталей.

| Операция | Что делает | Главный риск и решение |
|---|---|---|
| **Цековка** | цилиндрическое углубление под крепёж: `G82` с задержкой | глубина меньше диаметра — предупреждение; `Q` не нужен, но `R` обязателен |
| **Резьбовая фреза** | внутренняя/наружная резьба фрезой, спираль с шагом | шаг резьбы и число проходов считаются из `pitchMm` и `D`; на внешней резьбе — проверка «фреза не тоньше впадины» |
| **Гравировка** | однострочный текст по контуру | шрифт — встроенный однострочный (без внешних файлов), высота и наклон; буквы за пределами набора — ошибка «символ не поддержан» |
| **Карман с островом** | обход острова внутри кармана | припуск на остров; проверка «остров помещается между стенками»; сложный геометрический расчёт — отдельный этап зигзага со сбриванием |
| **Остаточная обработка** | обработка того, что не взяла предыдущая операция | требует карты высот или сравнения площадей: в MVP — по **геометрическому остатку от предыдущих карманов** в документе, без симуляции; если данных нет — предупреждение, а не молчание |
| **Импорт DXF** | контур из файла чертежа | читатель DXF с ограниченным набором сущностей (`LINE`, `LWPOLYLINE`, `ARC`, `CIRCLE`) и преобразованием в полилинию; файл **не хранится** в панели, только результат — контур в документе |

Оценки — как в §9: Q4 6-8 недель, Q5 8-12, но после двух заходов (7.3 и 7.4) диапазон уточняется по факту:
одна операция MVP-уровня с формой, выводом, `.qprog` и проверками занимает один заход из 4-6 задач.

## 8. Проверки и безопасность

* Генерация запрещена при `ESTOP`, занятости и невалидной таблице инструмента; форма проверяет `isBusy(s)`.
* Валидация возвращает `{ ok } | { bad: { field, reason } }`; каждое правило привязано к полю, а не к одной
  строке внизу. Тексты русские, причина — словами оператора.
* Проверки: инструмент влезает в карман (диаметр, радиус угла), глубина не ниже дна, шаг врезания больше
  нуля, подача и обороты в пределах станка, `WCS` существует, безопасный `Z` выше заготовки, нет быстрых
  ходов в материал, операция не целиком вне заготовки, инструмент задан.
* Предпросмотр обязателен; 2D-предпросмотр строится из `CamPath`, а не из второй геометрии. Простая
  коллизия — через вьювер; ошибка блокирует сохранение.
* `CAM_WRITE` — единственная точка записи. Имя файла по умолчанию (дата + операция), проверка существования
  и подтверждение замены. `CAM_CANCEL` не оставляет ни предпросмотра, ни файла.
* Первый запуск — с подтверждением и без автоматического старта.
* Опасные сочетания (инструмент больше кармана, тонкая стенка, пустой список) объясняются словами.
* Предпросмотр пересчитывается после debounce 150-200 мс. Если генерация дольше ~100 мс, планировщик уходит
  на рабочий поток; число измеряется, а не угадывается.

## 7.2 Демо-приложение на C++ (Q0, первый заход)

Заказчик просит обкатать быстрое программирование отдельно, на C++, до того как это появится в панели.
Отдельное приложение для этого обязательно: основной конвейер — React/TypeScript, Qt-порт отстаёт
(`docs/PORT-QML.md`), а C++ в проекте уже второй родной язык (ядро вьювера). Демо повторяет §7 в C++ и
проверяется из консоли, без Qt, — поэтому его можно гонять на любой машине с компилятором.

**Решение.** Новый проект `quickprog` — `apps/quickprog` (C++17, только стандартная библиотека):

* `core/geom.h` — точки, прямоугольник, окружность, полилиния, прямоугольник с радиусом угла;
* `core/ops.h` — `Program`, `Operation` (общие поля §6: инструмент, режимы, `topZ`, `depth`, `stepDown`,
  припуск), варианты `Face`, `RectPocket`, `CirclePocket`, `Drill`, `DrillGrid`, `DrillCircle`;
* `core/validate` — правила §8 как `Check { field, reason }`: инструмент влезает в карман, глубина не ниже
  дна, шаг врезания больше нуля, подача и обороты в допустимых пределах, безопасный `Z` выше заготовки,
  операция не целиком вне заготовки;
* `core/feeds` — режимы из диаметра, материала и типа инструмента по тем же числам, что `calc.ts`
  (единая таблица, не вторая формула);
* `core/path` — планировщик `Operation -> Path` (ходы `rapid`/`cut` с `feed`, без строк УП): торцевание
  полосами с перекрытием, прямоугольный карман зигзагом с чисткой стенки, круглый карман спиралью от центра,
  сетка и круг отверстий, один сверлильный цикл на точку;
* `core/emit` — `Path -> .ngc`: шапка `G21 G90 G94 G17 G40 G49 G80`, `G54`, безопасный `Z`, `T`/`M6`,
  `S`/`M3`, `M8`, теги `UI_STOCK`/`UI_OP`/`UI_TOOL`/`UI_ORIGIN` в комментариях (контракт с вьювером,
  `core/ui_tags`), сверление `G81`/`G83`, финал `M9 M5 G0 Z<safe> M30`;
* `cli/` — консольный сценарий (`main.cpp` — тонкий диспетчер): заготовка и инструмент аргументами или
  `--demo`, операции из файла `<имя>.qprog` (плоский текстовый формат, схема 1), вывод `<имя>.ngc`, печать
  сводки (ходов, длина, режимы с источником, оценка времени, предупреждения);
* `tests/` — собственная проверка без внешнего фреймворка: таблица случаев, каждая операция даёт ожидаемые
  числа (число проходов, площадь резания против квадратуры, отсутствие захода в стенку для кармана;
  перекрытие полос 20-30 % и отвод по краям для торцевания; координаты сетки и круга, `R`-плоскость и
  глубина, `Q` для `G83`); плюс round-trip: сгенерированная УП разбирается `gv::parseGcode` из ядра
  вьювера, модальные коды и число сегментов не ноль. Возврат: 0 — всё сошлось, 1 — есть расхождение.

Каркас сборки — `CMakeLists.txt` (Qt и OCCT для ядра генерирующей части не нужны; зависимость от `gvcore` —
только у проверки round-trip, это отдельная цель `quickprog_check`). Сборка на Linux —
`scripts/build-quickprog.sh`; на Windows — `scripts/build-quickprog.ps1`. Портативные бинарники — `build/quickprog/`.
`tools/checks.txt` пополняется строкой `quickprog (демо)`, но только когда сборка реально доступна:
`tools/check.sh` знает три требования (`probe`, `plugin`, `frame`), и строка с иным словом печатается
красной. Нужно четвёртое требование `quickprog` (готовность `build/quickprog/quickprog_check`) и шаг в
`tools/check.ps1`; до этого демо в стороже не участвует — запись в `TODO.md`.

**Что демо НЕ делает:** нет экрана и жестов (это P1 и панель), нет `.qprog` в формате React, нет запуска на
станке, нет коллизий через вьювер. Демо доказывает конвейер `операции -> Path -> .ngc` и отдаёт числа для
технолога.

**Чего ждём от демо (приёмка Q0):** файл, созданный для каждой MVP-операции, читается вьювером
(`gcodeviewer --smoke` и offscreen: `loaded OK`, теги `UI_*` на месте); для каждой операции есть случай
в `tests/` с числом проходов и границами; `.ngc` открывается глазами и объясняется технологом; режимы
резания берутся из таблицы и печатаются с источником.

## 9. Этапы и оценка

Оценки — для одного сильного разработчика без ожидания станка; это ориентир, не обещание.

| Этап | Что | Объём |
|---|---|---|
| Q0 | контракт операций, макеты формы, доменная проверка технологом, тонкий прототип экрана | S-M |
| Q1 | вертикальный срез: прямоугольный карман от формы до `CamPath`, `emit`, 2D-предпросмотра, файла и тестов | M |
| Q2 | торцевание, сверление, список операций и `.qprog`; три операции в одной программе | M |
| Q3 | проверка вьювером, время, коллизия, debounce/бюджет, три конфигурации | M |
| Q4 | контур, паз, метчик, фаска, массивы/поворот, `Custom G Code`, блок щупа | M-L |
| Q5 | цековка, резьбовая фреза, гравировка, остров/остаток, DXF | L |
| Q6 | прогон на реальной УП и станке, операторская приёмка, документация | M |

Ориентир MVP Q1-Q3: **6-8 недель**; P1 Q4: **+6-8 недель**; P2 Q5: **+8-12 недель**; полировка и станок
Q6: **+2-4 недели**. После Q0 диапазон уточняется по прототипу. Q1 — вертикальный срез, не релиз: без Q2
он не решает задачу детали из нескольких операций.

## 10. Тесты и приёмка

* На каждую операцию — тест геометрии, глубины, шага, припуска и границ. Для кармана: площадь резания
  против квадратуры, число проходов, отсутствие захода в стенку, точки у стены, врезание.
* Торцевание: перекрытие полос 20-30 % диаметра, отвод по краям. Сверление: координаты сетки/круга,
  `R`-плоскость, глубина, `Q` для `G83`.
* Золотые `.ngc` для маленьких случаев: торцевание, карман, круг, сетка отверстий; сравнение строк и
  координат.
* Валидация: каждое правило даёт `field + reason`; инструмент больше кармана, глубина ниже дна, пустая
  программа, отрицательный шаг, операция вне заготовки.
* `parseWords` round-trip: сгенерированная УП разбирается парсером панели, модальные коды совпадают. Это
  проверка синтаксиса, а не геометрии: дуги и циклы дополнительно проверяются вьювером.
* Предпросмотр строится из `CamPath` и совпадает с `emit` на контрольных случаях.
* Сгенерированная УП грузится вьювером: `--smoke`, `loaded OK`, без `[QML warning]`, сегменты и `UI_*`
  читаются.
* `cam.ts`: `isBusy` блокирует, `CAM_CANCEL` чист, запись только через `CAM_WRITE`, существующий файл
  требует подтверждения.
* Три конфигурации: P1 без касания, P2 клавиши и касание, P3 только касание.
* Приёмка оператора: карман отдельно, затем 3 операции в одной программе, сохранить, открыть, проверить,
  запустить на демо-детали.

## 11. Риски и открытые вопросы

| Риск | Что делать |
|---|---|
| Контур и коррекция на радиус дают зарез | в MVP только центр траектории; `G41/G42` отдельным этапом |
| Вьювер не понимает часть циклов | MVP — `G81/G83`, дуги проверить; `G84` только после |
| Много полей на 1024x600 | вкладки, подсказки, крупные цели; проверка на P1/P2/P3 |
| Модель и `.ngc` расходятся после ручной правки | `.ngc` помечен generated; при ручной правке — предупреждение |
| LinuxCNC GPL | не копировать код; свои алгоритмы, только идеи интерфейса |
| Режимы резания «на глаз» | брать из материала/инструмента, показывать источник и разрешать правку |
| Неявная операция даёт неожиданный результат | явная траектория, сводка параметров и предупреждения; `Custom G Code` отдельно |
| Одной операции мало для детали | Q1 — только вертикальный срез; Q2 обязательно добавляет список и три операции в одной программе |
| `parseWords` не проверяет геометрию | геометрические тесты + `gcodeviewer --smoke`/offscreen; не считать round-trip доказательством |
| Генерация подвешивает GUI | debounce 150-200 мс, бюджет ~100 мс, затем рабочий поток |
| Запись затирает чужую УП | `CAM_WRITE` только с именем, подтверждением замены и резервной копией/отменой |
| `G41/G42` не решён | MVP — явный центр траектории и `G40`; коррекция отдельным этапом |
| Коллизия названа, но не определена | в MVP — существующая проверка вьювера; в 2D — `UNVERIFIED`, не «чисто» |

Открытые вопросы: точный список MVP-операций; нужен ли дюйм; нужен ли контур сразу; формат `.qprog` и
место хранения; использовать ли O-подпрограммы позже; кто даёт таблицу материалов и режимы; нужен ли DXF
в ближайшей версии. Версии этапов не фиксируются числами `0.19`-`0.24`: они привязаны к M5 и текущему
релизу, иначе план устареет через один коммит.
