# PORT-QML.md — перенос панели оператора из React в Qt (QML)

Документ о **намеченной** работе: приведение Qt-порта панели (`apps/qt-interface/main.qml`)
в соответствие с React-панелью (`apps/react-interface`). Источник истины о поведении — код и
его прогон; здесь — замысел, якоря в файлах обеих сторон и приёмка.

Редакция объединена 31.10.2026: инвентаризация и якоря — от предыдущей редакции плана,
порядок работ, приёмка и решения — от lead'а. Состояние на день редакции: React `0.24.0`
(продукт `0.34.0`), Qt `0.5.8`.

**Роли зафиксированы (01.11.2026).** На реальной стойке работает **Qt — это продукт**. React был
демо-сценой: после исправления запуска и вставки CAM он **заморожен** — новые возможности в нём
не ведутся. React остаётся эталоном текстов, поведения и тестов для сверки; найденный при
переносе дефект чинят в React и сразу переносят в Qt.

Порт существует и не пуст: `main.qml` — 3558 строк, `preview.qml` — ручная копия той же панели
(3567 строк; правится руками вместе с `main.qml` до волны A), `assets/` и `fonts/` рядом.
Сверка текстов заведена: `apps/react-interface/lib/cnc/qt-parity.test.ts` держит 19 общих
подписей и читает только `main.qml`. Правило — `CLAUDE.md`, раздел 5: **порт сверяют с
оригиналом дословно, а не переводят заново**; расхождение обязано краснеть в тесте, а не
всплывать на экране оператора.

**Почему план переписан.** Прежняя редакция описывала React `0.20.8`; с тех пор вышли волны
0.21–0.23 (быстрое программирование в панели) и 0.28 (замечания оператора: обмер инструмента
окном F1, клавиатура 6×5, блок «Инструмент» со следующим инструментом, «Обдув»/«Промывка»,
порядок боковой колонки). Инвентаризация в §1 собрана заново с якорями в коде обеих сторон,
чтобы исполняющий агент не искал «где это живёт».

**Как пользоваться планом.** Волны §4 идут по порядку; каждая — отдельный заход со своей
приёмкой по воротам G (`AI_WORKFLOW.md`, раздел 4). Шаги ссылаются на файлы и имена функций;
номера строк — подсказка, а не контракт: если символ не найден, работу останавливают и
возвращают lead'у. Решения распорядителя — §7.

## 2. Правила переноса (действуют для всех волн)

1. **Источник текстов и наборов — React.** Подписи берутся из `SOFTKEY_LABEL` и соседних таблиц
   `data.ts`/`types.ts`; новых названий в QML не сочиняют. Сверку наращивают на каждый новый
   узел.
2. **`preview.qml` — обёртка, а не копия.** В волне A он становится окном на ~10 строк над
   `main.qml` (`Main { anchors.fill: parent }`); ручная копия на 3567 строк удаляется. Это
   снимает целый класс расхождений и не требует «править два файла одинаково».
3. **Машинный манифест — только тексты и наборы.** Генератор из `lib/cnc` выгружает
   `apps/qt-interface/panel-data.js`: вкладки и подписи, рабочие места, наборы F1–F8
   `{ id, label }` по рабочему месту и экрану, `MODE_LABEL`, `SCREEN_LABEL`, `SOFTKEY_LABEL`.
   Формат — QML-совместимый JS-модуль (`.pragma library`), не JSON. Свежесть проверяет сторож.
4. **Токены тем — отдельно от манифеста текстов.** CSS-оверрайды `.theme-minimal` (~350 строк)
   не разбирают регулярками. Один TS-файл токенов (или разовый генератор из CSS) — источник;
   сторож сверяет его с `globals.css`, QML читает готовые пары имя -> значение.
5. **Повторяют поведение, не код.** Редьюсер, React-компоненты и Tailwind в Qt не переносят;
   те же правила (занятость станка, аварийный стоп, причина отказа) выражают короткими
   функциями рядом с `root` или внутри выделенных компонентов. Одна таблица «id действия ->
   поведение»; особых путей для отдельных клавиш нет.
6. **Разбивают, а не дописывают монолит.** Новые узлы — отдельными QML-компонентами рядом с
   `main.qml` (`SoftkeyBar.qml`, `WorkScreen.qml`, `AutoScreen.qml`, `PendantWindow.qml`,
   `MpgWindow.qml`, `ToolMeasureDialog.qml`, `Theme.qml`, `TouchDeck.qml`). `main.qml` —
   каркас: шапка, вкладки, стек экранов, бар. Размер файлов держит сторож.
7. **Версии раздельные.** Порт меняет `qt-interface` и версию продукта; `react-interface`
   поднимают только если правили его код или тексты (`VERSIONING.md`, раздел 2). Вьювер и
   тестовые данные не задеваются. Журнал — корневой `CHANGELOG.md`.
8. **Проверка — прогоном, а не глазами.** Автоматический `panel_probe` (offscreen-загрузка QML)
   проверяет числа и наборы; `preview.qml` — визуальная проверка без 3D; экран АВТО с
   траекторией — в живом окне вьювера. Скриншот ключевого состояния кладут в `img/`.
9. **Панель 1024×600, слово влезает в слот.** Длина подписи софт-кея — до
   `SOFTKEY_LABEL_MAX = 14` символов; это часть проверки, не вкус. Длину остальных подписей
   (вкладки, шапка) проверяют тем же пробником.
10. **Работа без сенсора — равноправный режим.** Каждый экран, диалог и действие доступны с
   физических кнопок и клавиатуры: `F1`..`F8`, стрелки, `Tab`, `Enter`, `Esc`, цифры, джойстик и
   маховик. Сенсор — дополнительный способ, а не единственный; мышь и hover не обязательны.
   Это проверяют сценарием «только клавиатура» на каждом экране, а не глазами.

## 4. Волны и шаги

Каждая волна заканчивается приёмкой, которая краснеет при расхождении. Оценки грубые, для
распорядителя. «Пред.» — предусловия; шаги выполняют по порядку; после шага проверки зелёные,
прежде чем идти дальше.

### Волна A. Фундамент (2-3 дня)

Пред.: нет.

1. **`preview.qml` — обёртка.** Заменить копию на `Window 1024×600` с `Main { anchors.fill:
   parent }`; проверить, что `main.qml` регистрируется как тип `Main` из того же каталога и
   FontLoader находит `fonts/`. Приёмка: `preview.qml` короче 20 строк, панель запускается так
   же, как раньше.
2. **Генератор `panel-data.js`.** Скрипт на стороне `react-interface` (TypeScript рядом с
   `lib/cnc`, запуск через `pnpm`) выгружает вкладки/подписи, рабочие места, наборы F1–F8 по
   рабочему месту и экрану (id + label, без поведения), `MODE_LABEL`, `SCREEN_LABEL`,
   `SOFTKEY_LABEL`. Формат — JS-модуль для QML, не JSON; русский текст в UTF-8.
3. **Сверка читает весь порт.** `qt-parity.test.ts` обходит `apps/qt-interface/**/*.qml`, а не
   только `main.qml`; для каждого набора сверяет id и подписи слотов, 5 вкладок и подписи
   рабочих мест. Старые 19 строк `SHARED` не удаляют до конца волны C.
4. **`panel_probe` — скелет.** Offscreen-загрузка `main.qml` и проверки: 5 вкладок, 8 слотов,
   список тем, текст без U+FFFD. Запуск из сторожа, без ручного участия. (До волны B проверки
   могут быть `xfail` — важно, что механизм есть.)
5. **Сторож.** Шаг в `tools/check.ps1`: пересобрать `panel-data.js` и сравнить с коммиченной
   копией; расхождение — `FAIL` с именем поля. Версии и `CHANGELOG.md` — в том же коммите.
6. **Точка входа продукта.** Панель запускается на стойке не через `qmlscene`: нужен штатный
   запуск (QtVCP/загрузчик QML или собственный exe без консоли) с путями к `MockBackend` и
   `CNC.Edges`. `qmlscene` остаётся только для отладки. Версия Qt-порта поднимается в том же
   коммите.

Проверки: `pnpm test`, `pnpm guard`, запуск `preview.qml`.
Приёмка: правка подписи в `data.ts` без пересборки манифеста краснеет; копии `preview.qml` нет;
`panel_probe` запускается сторожем.
Риск: манифест неудобен QML. Решение: JS-модуль (решено), проверено на одном наборе до
выгрузки всех.

### Волна C. Рабочие места, состояние и наборы (3-4 дня)

Пред.: A, B.

1. Свойство `workplace` (`SETUP`/`TEST`/`RUN`), три кнопки в порядке АВТО, ПРОГОН, НАЛАДКА;
   `setWorkplace()` — зеркало `nav.ts`: при занятости отказ с сообщением, `SETUP` -> `JOG`,
   `TEST`/`RUN` -> `AUTO`, `dryRun = (wp === 'TEST')`.
2. `machineMode` становится производным от `workplace` + ручного перевода; один источник.
3. Снять `tabLocked`; запреты переезжают в действия (`guards.ts`): запись смещения при
   занятости, движение при аварийном стопе.
4. Наборы F1–F8 из манифеста: окно -> рабочее место -> экран, как `getSoftkeys`. Таблица

5. Причина отказа: замок и подсказка у отключённой клавиши; нажатие печатает `reason` в строку
   сообщений (умолчание `FALLBACK_REASON`).

Проверки: `panel_probe` (наборы по рабочим местам, причины), `preview.qml` в каждом режиме.
Приёмка: перебор рабочих мест меняет экран, режим и набор; ни одна вкладка не зачёркнута;
отключённая клавиша называет причину.
Риск: две системы режимов. Решение: `machineMode` производный (шаг 2).

   каталога, а не `viewSample`). После этого временная вкладка «3D» удаляется.
4. Покадровый просмотр и «Старт с кадра» (`PROG_TO_CURSOR`), восстановление модальных кодов.
5. Редактор УП и поиск/замена.

Проверки: `panel_probe`; `preview.qml` — виды и полоса без 3D; живое окно — траектория, окно
кода, покадровый ход.
Приёмка: F8 обходит 4 вида; «Обработка» не скрывается; окно кода не перекрывает заголовок; УП
грузится из каталога.
Риск: offscreen не рисует Quick3D — часть проверок только в живом окне (помечают `UNVERIFIED`).

### Волна E. Мастера, темы, сенсор (6-8 дней)

Пред.: C, D (окна софт-кеев из C).

1. `ToolMeasureDialog.qml`: параметры подвода, сцена датчика, фазы
   `idle->rapid->fine->touch->retract->done` с теми же таймингами; F1 в НАЛАДКЕ только
   открывает окно, запуск — «Пуск замера» внутри; аварийный стоп прерывает.
2. Мастер щупа: шаги `PROBE_STEPS`, правила `probe.ts`, требование `PROBE_TOOL = 99`, запись
   результата в смещение (сейчас `pWrite` закрывает), повтор.
3. Окна софт-кеев (`fileDialog`, `toolDialog`, `calc`, `search`, `toolMeasure`): правило окна
   вытесняет набор экрана.
4. `Theme.qml`: 6 тем из отдельного токен-источника; «Минимал» — 1 px линии, зазор 0,
   скругление из `--radius`, без теней; жёсткие `radius:` заменяются токеном.
5. `TouchDeck.qml`: сенсорная колода, софт-кеи без F-подписей, ряд Пуск/Стоп/Сброс/Авария
   только на «Работе», MDI в нижней зоне НАЛАДКИ, «совместно» вертикально; режим — параметр
   `[DISPLAY] UI_MODE`.

Проверки: `panel_probe` (темы, шаги щупа), `preview.qml` в каждой теме и в двух режимах.
Приёмка: обмер до записи длины; аварийный стоп прерывает; шаг измерения требует T99; запись
пишет в смещение; смена темы сохраняет геометрию; в сенсорном режиме нет F-подписей.
Риск: портрет 1080×1920 не помещается в превью 1024×600 — проверяют отдельным окном, честно
помечают.

### Волна F. Эмуляторы пультов: клавиатура и MPG (3-4 дня)

Пред.: B, C (общая таблица действий и шапка).

Назначение — отладка на реальном железе до появления физического пульта. Окна — **отдельные
окна** над панелью, не часть основного экрана.

1. **`PendantWindow.qml`** — виртуальный пульт: сетка 6×5 (цифры без Shift, прямые буквы
   `G M X Y Z S F T N O A B C D`), клавиши 72×72, клавиши `Пуск/Стоп/Сброс/Авария`,
   `Обдув/Промывка/СОЖ/Маховик`, джойстик, множители, шпиндель/подача/ускорение.
   Поведение берётся из той же таблицы действий, что у основного экрана: отдельной логики у
   окна нет.
2. **`MpgWindow.qml`** — эмулятор маховика: выбор оси `X/Y/Z/A`, множитель `×1/×10/×100`
   (`MPG_STEPS`), колесо (перетаскивание или кнопки `+/-`), импульсы уходят тем же действием,
   что у физического MPG; шаг на импульс — из выбранного множителя.
3. **Открытие из интерфейса.** В сервисном экране раздел «Отладка» (или отдельный софт-кей
   `[DEBUG]`) — кнопки «Виртуальный пульт» и «MPG-пульт». Окна — `Window` с `visible` от
   свойства `root`; повторное нажатие поднимает существующее окно, второе не создаётся.
   В обычной работе раздел скрыт, чтобы не мешать оператору.
4. **Безопасность.** Окна — инструмент отладки: действия проходят те же запреты (занятость,
   аварийный стоп), что и с основного экрана; окно не обходит `guards.ts`.
5. **Приёмка на железе.** В QtVCP окно открывается поверх панели, клавиша пульта меняет то же
   состояние и строку сообщений, что физическая клавиша; MPG при `×10` сдвигает ось ровно на
   0.01 мм за импульс; закрытие окна не сбрасывает состояние.

Проверки: `panel_probe` — окна открываются/закрываются, повторное открытие не плодит окна;
`preview.qml` + живое окно; скриншот пульта и MPG в `img/`.
Приёмка: обе кнопки в «Отладке» открывают отдельные окна; действия совпадают с основным
экраном; MPG двигает выбранную ось с выбранным шагом.
Риск: второе окно требует `Window` и `QtQuick.Window`; в QtVCP это поддерживается, но
проверяют именно в том рантайме, где запускают панель.

### Волна G. Быстрая УП (CAM) — отдельная работа (8-12 дней)

Пред.: волна A (ядро C++ можно вести параллельно с B/C/D).

**Что уже есть.** CAM реализован в React на TypeScript: `lib/cnc/cam/` (141 файл, 15 видов
операций, планировщик, эмиттер, `.qprog`, тесты) и `components/cnc/cam/` (25 файлов, оверлей).
В C++ есть только консольное демо `apps/quickprog`: 608 случаев самопроверки, планирует
**четыре** вида (торцевание, карман, круглый карман, сверление), читает `.qprog` всех 15 видов,
а непланируемые пропускает строкой в сводке. Панельного CAM на C++ и Qt нет.

**Вход (исправлено в `0.33.2`).** Раньше в React-панели к CAM не было пути через интерфейс:
софт-кей «Быстрая УП» был объявлен только в `progScreen` и перекрывался наборами рабочего места
(`testWorkplace`/`runProg`) и набором редактора. Теперь F8 «Быстрая УП» есть в режиме правки УП,
и тем же слотом оверлей закрывается; слот держит тест софт-кеев. Оператор либо правит открытый
файл, либо создаёт новый и вызывает быструю УП из редактора.

1. **Носитель — C++-ядро (решено, §7).** Растить `apps/quickprog` до 15 видов: типы и `.qprog`,
   затем планировщики видов, затем эмиттер. QML получает ядро как библиотеку с тонкой обёрткой
   (тип/фасад), не копию алгоритмов. TypeScript-реализация остаётся эталоном для сравнения
   выходной УП, а не вторым носителем.
2. **Порядок видов.** Сначала 4 уже перенесённых (торцевание, карман, круглый карман,
   сверление) сверить с React побайтово, затем добавлять остальные по одному: контур, паз,
   фаска, резьба метчиком, цековка, резьбовая фреза, гравировка, карман с островом, остаточная
   обработка, щуп, произвольный G-код. Каждый вид закрывают тестом на эталон.
3. **`CamOverlay.qml`:** список операций, формы, предпросмотр, сохранение с `.bak`, вставка в
   открытую УП, проверка УП.
4. **Открытие** — с экрана ПРОГОН, как в React; в сенсорном режиме — отдельной кнопкой. Вход в
   React-редакторе уже восстановлен (`0.33.2`), в Qt его делают в этой волне.
5. **Параллельность.** Ядро C++ можно вести параллельно с волнами B/C/D: оно не зависит от
   каркаса QML. Это длинный полюс (8–12 дней), поэтому старт — сразу после волны A.

Проверки: C++ `quickprog_check`, новые тесты видов, golden-сравнение УП, `panel_probe`.
Приёмка: все 15 видов планируются и дают ту же УП, что React на демо-детали.
Риск: два источника алгоритмов. Решение: носитель один — C++-ядро; TypeScript остаётся
эталоном для сравнения, второй реализации в продукте нет.

### Волна H. Работа без сенсора: физические кнопки (2-3 дня)

Пред.: волны A-F; закрывается после них, потому что проверяет все экраны сразу.

Цель — панель полностью управляется с физического пульта и клавиатуры, без касаний и мыши.

1. **Полная карта клавиш.** Для каждого действия на экране есть клавиша или последовательность:
   `F1`..`F8` — софт-кеи, стрелки/`Tab` — фокус и списки, `Enter` — пуск/подтверждение,
   `Esc` — сброс/закрытие, цифры — вкладки и ввод, буквы — MDI. Карта сверяется с `keys.ts` и
   набором софт-кеев: нет действия без клавиши, нет клавиши без подписи.
2. **Фокус и выбор.** Видимое кольцо фокуса, курсор в списках и таблицах, `PgUp`/`PgDn`,
   переход по формам `Tab`/`Shift+Tab`, `Enter` в поле — подтверждение. Подсказки не зависят от
   наведения мыши; отключённая клавиша называет причину в строке сообщений.
3. **Раскладка панельного варианта.** Экран не требует сенсорных зон: тач-колода и крупные
   сенсорные кнопки скрыты или свёрнуты, их действия доступны с пульта. 1024×600, подписи
   влезают в слот.
4. **Диалоги без жестов.** Все окна (файл, инструмент, калькулятор, поиск, обмер, щуп, CAM)
   открываются, обходятся и закрываются с клавиатуры. Перетаскивание — необязательный способ:
   для списков и полей есть клавиши; эмулятор MPG работает и с клавиатуры (`+`/`-`, стрелки).
5. **Сценарий «только клавиатура».** Пройти полный путь оператора без касаний и мыши: пуск,
   выбор программы, правка, CAM, сохранение/вставка, проверка, старт с подтверждением, стоп,
   сброс. На каждом экране — скриншот и запись нажатий.

Проверки: тесты маршрутизации клавиш (`keys.test.ts`), `panel_probe` (фокус и клавиши), прогон
`preview.qml` без мыши, скриншоты в `img/`.
Приёмка: ни одно действие не требует касания; сценарий пройден только клавиатурой; каждое
действие имеет подпись клавиши; отключённая клавиша объясняет причину.
Риск: сенсорные жесты (свайп, перетаскивание) могут остаться единственным способом в отдельных
местах — их находят сценарием и добавляют клавишу.

## 5. Порядок и оценка

Сначала A -> B -> C: после них каркас, рабочие места и наборы сверяются машинно, а первый
видимый результат появляется уже в B. Затем D (экраны и вьювер), E (мастера, темы, сенсор),
F (эмуляторы для отладки на железе). CAM (G) — отдельная волна, но её C++-ядро ведут
**параллельно** с B/C/D: это длинный полюс и он не зависит от каркаса QML. H (без сенсора)
закрывается после A-F.

Грубая оценка: A 2-3, B 3-4, C 3-4, D 4-6, E 6-8, F 3-4 дня — **21-29 дней** одного человека
до визуального паритета; H (работа без сенсора) — ещё **2-3 дня** и закрывается после A-F;
G (CAM) — **8-12 дней** отдельно.

**Первый заход.** Начать с **A (фундамент)** и сразу за ним **B (видимый каркас)**: после B
панель уже выглядит как React и её можно показать на стойке. Параллельно, не дожидаясь B,
запустить **C++-ядро CAM (G, шаги 1-2)**: это длинный полюс, и он не зависит от QML. C и F —
следом; D — после C; E — после D; H — приёмка после A-F.

## 6. Риски общего вида

* **Монолит.** `main.qml` в 3558 строк разрезают по волнам (правило §2 п.6); без этого правки
  перестанут помещаться в голову. Сторож на размер — как метка `machine.ts`.
* **Три источника текстов.** Пока есть React, QML и манифест, расходиться могут любые два.
  Манифест (волна A) закрывает это машинно; без него волны B-E снова разойдутся руками.
* **Ручная копия `preview.qml`.** До волны A — риск; после — обёртка, копии нет.
* **Два пульта.** Виртуальный пульт (волна F) не должен завести вторую таблицу действий:
  только общая. Иначе клавиша на экране и на пульте разойдутся.
* **Рантайм Qt.** Панель стартует только в рантайме с плагином `MockBackend`
  (`build/qmlbackend/...`); `qml` другой минорной версии модуль не загрузит
  (`docs/PORT-CPP.md`, §11). Проверяют в том рантайме, в котором запускают панель.
* **Живой 3D только в окне.** Offscreen не рисует Quick3D; экран АВТО с траекторией принимают
  в живом окне.
* **CAM — второй носитель.** TypeScript остаётся эталоном, продукт — C++-ядро; второй
  реализации в продукте нет, иначе алгоритмы разойдутся.

## 7. Решения распорядителя (зафиксировано 31.10.2026)

1. **Манифест `panel-data.js` — делать** (волна A). Генератор живёт в `react-interface`
   (`lib/cnc` — источник текстов), сторож — в `tools/check.ps1`.
2. **Вьювер — дочерний элемент панели** в экране АВТО (не отдельное окно); загрузка УП из
   каталога, связка с `docs/PORT-CPP.md`.
3. **Сенсорный режим — переносить** (волна E полностью).
4. **Темы — все 6**, токены «Минимал» из отдельного TS-источника, а не руками.
5. **Виртуальный пульт — нужен, отдельным окном** из интерфейса (волна F). Он нужен для
   отладки на реальном железе, пока нет физической панели.
6. **Эмулятор MPG-пульта — нужен, отдельным окном** из интерфейса (волна F), с выбором оси и
   множителя, теми же действиями, что у физического маховика.
7. **`preview.qml` — обёртка**, ручная копия удаляется (волна A).
8. **CAM (быстрая УП) — отдельная волна** (G): C++-ядро растят параллельно с B/C/D, оверлей —
   после каркаса; носитель — C++ (решение 11).
9. **Работа без сенсора — обязательна** (волна H): каждый экран и диалог управляются с
   физических кнопок и клавиатуры, сенсор — дополнительный способ.
10. **Qt — продукт, React — эталон.** На стойке работает Qt; React заморожен после стабилизации
    (запуск, вставка CAM) и служит эталоном текстов, поведения и тестов. Новые возможности —
    только в Qt.
11. **CAM — на C++-ядре.** `apps/quickprog` растят до 15 видов и отдают QML обёрткой; TypeScript
    остаётся эталоном для сравнения выходной УП, второй реализации в продукте нет.

## 8. Чем этим планом не занимаются

Перенос вьювера (отдельный план — `docs/PORT-CPP.md`), правки самого React-интерфейса,
тестовые УП и постпроцессор. CAM — волна G: её C++-ядро стартует параллельно с B/C/D, оверлей —
после каркаса.
