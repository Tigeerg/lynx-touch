# Журнал изменений — 3D-вьювер G-кода (QtQuick3D)

Файлы, которых касались изменения:

| Файл | Назначение |
|------|-----------|
| `modules/gcode-viewer/mock_backend.py` | Python/Qt-бэкенд: парсер G-кода, геометрии (траектория, сетка, меш, контуры), расчёт трансформа детали |
| `modules/gcode-viewer/GcodeViewer3D.qml` | Сам вьювер: сцена, камера, материалы, анимация, оверлей загрузки |
| `modules/gcode-viewer/preview_3d.qml` | Обёртка `Item -> Window` для запуска вьювера |
| `modules/gcode-viewer/preview_3d.py` | Точка входа: запуск окна, загрузка УП |
| `modules/gcode-viewer/toolpath.vert` / `toolpath.frag` | Шейдеры кастомного материала для скрытия пройденных линий |
| `modules/gcode-viewer/stepledges.vert` / `stepledges.frag` | Шейдеры ленточной обводки: постоянная толщина в px, distance-field AA, polygon offset в клип-пространстве |
| `modules/gcode-viewer/test_tangent_policy.py` | Headless-проверка политики касательного контура на STEP-модели |
| `modules/gcode-viewer/test_ribbon_width.py` | Живая проверка толщины ленты (2 px по вертикали и горизонтали) |
| `modules/gcode-viewer/test_solid_skin.py` | Живая проверка: сплошная кожа закрывает скрытые рёбра (без просвечивания) |
| `modules/gcode-viewer/render_probe.py` | Диагностический захват кадра (режимы: none/model/async, pitch=, yaw=, nostock) |

Запуск: `python modules/gcode-viewer/preview_3d.py "путь/к/файлу.ngc"` (STL с тем же именем подхватывается автоматически).

**Текущая версия вьювера:** `0.12.1` (см. `modules/gcode-viewer/VERSION`).

## История версий

### 0.12.1 — 2026-10-15

- **Cam-float рёбер перенесён из CPU-репака в вершинный шейдер.** На каждое движение камеры
  `refreshTangents` перепаковывал статические B-rep рёбра (18986 сегментов на Test_model) ради
  сдвига вдоль луча зрения, причём сдвиг был выключен (`CAM_FLOAT_MM = 0.0`) - то есть ~21.6 мс
  GUI-потока на кадр уходило на смещение на ноль миллиметров, а событие камеры стоило ~29 мс
  против бюджета 4 мс из `bench_viewer.py`. Теперь сдвиг делает `stepledges.vert` по uniform'ам
  `eyeRaw` (глаз камеры в raw-кадре модели, пересчитывается в `refreshTangents`) и `camFloatMm`
  (значение - свойство материала в QML, менять его можно без правки Python); статические рёбра
  заливаются в GPU один раз на модель, а `set_segments` лишился параметра `eye`. Замер той же
  методикой: событие камеры ~29 -> ~9.5 мс. FPS в покое не меняется - без движения камеры кадр
  ограничен GPU, а не CPU.

### 0.12.0 — 2026-10-15

- **Счётчик FPS (клавиша F).** Кадровая частота показывается в правом верхнем углу,
  включается и выключается клавишей F; при выключении среднее сбрасывается в 0. Значение -
  экспоненциальное среднее `1/frameTime` с коэффициентом 0.9: мгновенное `1/frameTime` на
  vsync-мониторе стоит ровно и читать нечего, единичный дроп кадра не должен бросать цифру,
  а реальный скачок виден за ~10 кадров. Счётчик использует отдельный `FrameAnimation` со
  свойством `running: root.showFps`, поэтому пока он выключен, накопления нет вовсе (в
  отличие от постоянного таймера). Строка подсказок дополнена «F fps: вкл/выкл».

### 0.11.2 — 2026-10-15

- **Загрузка STL падала на numpy-массиве (продолжение 0.11.1).** `load_stl_vertices` при
  установленном numpy возвращает массив формы `(N,3)`, а не список, и проверка `not verts` в
  `_stl_normals` выбрасывала `ValueError: The truth value of an array with more than one element
  is ambiguous`. Исключение ловилось в `_load_model_verts`, модель считалась загруженной без
  вершин, и дальше GUI-код шёл по ветке «модель есть» с пустыми данными - вплоть до падения в
  нативной памяти (`free(): invalid pointer`). Проверка заменена на `verts is None`; выражение
  `len(verts) < 3` для массива даёт число строк и работает как прежде. Проявлялось только там,
  где модель находилась: на Windows поиск не зависел от регистра, а без numpy `verts` - список.

### 0.11.1 — 2026-10-15

- **STL в верхнем регистре не находился рядом с УП (Linux).** Сайдкар искался только как
  `<имя>.stl` в нижнем регистре. На Windows `os.path.exists` к регистру нечувствителен, на Linux
  `.stl` и `.STL` - разные имена, и модель `CAD/Test_model.STL` не подхватывалась. Поиск STL во
  всех трёх местах (`_find_model`, fallback при сбое STEP в `_load_model_verts`, `_worker_load`)
  получил детерминированный перебор `.stl` -> `.STL` -> `.Stl`. Чтение самого STL уже было
  регистронезависимым (`low.endswith(".stl")`) и не менялось.
- **`UnboundLocalError: local variable 'norms'` при отсутствии модели.** В `_worker_load`
  переменная `norms` не была инициализирована и присваивалась только внутри ветки
  `if model_path:`. Когда модель рядом с УП не найдена, `self._model_normals = norms` падал в
  фоновом потоке загрузки: G-код грузился, деталь не подхватывалась. Инициализирована
  `norms = None` рядом с `verts`/`segs`.

### 0.11.0 — 2026-10-15

- **Силуэт по мешу вместо аналитических образующих (прототип варианта A).**
  View-зависимый контур строится по топологии меша кожи, а не по касательным
  образующим цилиндров/конусов STEP. Один раз на модель (на загрузке, в
  рабочем потоке `_load_model_verts`) вершины свариваются по округлённой
  позиции (допуск `1e-4` мм), строится карта «ребро (a,b) -> два смежных
  треугольника» и геометрические нормали/центроиды треугольников
  (`_build_silhouette_topology`). На ракурс для каждого ребра с двумя гранями
  берётся знак `n1.(eye-c1)` и `n2.(eye-c2)`: разные знаки - ребро лежит на
  горизонте поверхности, это силуэт (`_mesh_silhouette_segments`). Силуэт
  получает **любая** поверхность (плоскость, скругление, фаска, стенка
  отверстия) без предварительной раскладки граней по типам.
- **Убран слой эвристик аналитического генератора:** азимутальная ARC-маска
  покрытия, DROP-полоса подавления образующих у стыковых кромок, пороги
  покрытия (`>=56` корзин полного круга, `>=4` для частичной дуги), диапазон
  дуги `A0/A1` и гашение выпуклых скруглений. Меш-силуэт в них не нуждается:
  горизонт задаёт сам переворот нормали грани. Старые функции
  (`_tangent_families` / `_tangent_from_families`, `load_step_surfaces`)
  оставлены за флагом для сравнения.
- **Силуэт - только горизонт гладких поверхностей (фикс «заусенцев» и
  «удвоения»).** Первая версия меш-силуэта рисовала все рёбра с переворотом
  нормали, и это давало два дефекта: (1) острые кромки дублировались вторым,
  тесселированным контуром рядом с точной статической кромкой - «удвоение
  круглых линий» у отверстий/скруглений; (2) вырожденные/сляйверные грани
  (площадь ~1e-15 мм², 47+ штук в тесселяции) имеют нормаль-мусор, её знак
  скачет и рождает короткие ложные «усы» (диагностика на ракурсе pitch=-38
  yaw=17: degree>=3 вершины силуэта = 2, ветки 0.78 мм на таких гранях).
  Теперь `_build_silhouette_topology` оставляет кандидатами только гладкие
  переходы (`< _SILHOUETTE_MAX_EDGE_DEG = 20 град` - круче уже точно рисует
  слой статических B-rep рёбер) и без вырожденных граней
  (`area > _SILHOUETTE_MIN_FACE_AREA = 1e-6 мм²`). Горизонты стенок отверстий
  и скруглений сохраняются; контур плоских острых кромок даёт слой partEdges.
  Эффект: на проблемном ракурсе «усов» 0 (было 2), удвоения острых круглых
  линий нет; число силуэтных рёбер `Test_model` 4.6-6.3 тыс. -> 68-1383
  (только гладкие горизонты, view-зависимо).
- **cam-float 0.5 -> 0 мм (убраны короткие «штрихи» скрытых рёбер).**
  `HLRLineGeometry.CAM_FLOAT_MM` сдвигал линии К глазу вдоль луча зрения
  (проекционно-нейтрально, для запаса над буфером глубины). Но на скользящем
  контуре этот сдвиг вытаскивал из-под непрозрачной кожи короткий участок
  СКРЫТОГО силуэтного ребра - наблюдались «штрихи»/«усы» у торцов паза
  (ракурс pitch=-43 yaw=17 dist=56: длина штриха ~19 px при 0.5 мм, ~5 px при
  0.1, 0 при 0). Теперь cam-float 0: видимые линии держит клип-сдвиг
  `polyOffset` в `stepledges.vert` (проверка `test_ribbon_width`, толщина
  1.61 px), скрытые честно режет глубина (`test_solid_skin`).
- **Переиспользован конвейер обводки.** Сегменты публикуются в тот же слой
  `_hlr_tangents` (`HLRLineGeometry`): шейдеры ленты `stepledges.vert/.frag`,
  постоянная толщина в px, cam-float (смещение К глазу) и `depthBias -1000`
  без изменений. Статические B-rep рёбра (`partEdges`) остаются как есть - они
  точны для острых кромок.
- **Флаг режима:** переменная окружения `CNC_SILHOUETTE=mesh|analytic`
  (по умолчанию в этой ветке `mesh`). `analytic` включает прежние касательные
  образующие - для сравнительных прогонов и старой проверки политики.
- **Отсечение скрытого.** В сплошном режиме (X выключен) скрытые участки
  силуэта срезает GPU-глубина непрозрачной кожи - как и раньше. В рентгене
  (X включён) кожа `Blend` глубину не пишет, поэтому силуэт виден целиком
  («показать всё») - это осознанное поведение поиска дефектов, а не отсечение.
- **Производительность (замер, numpy, PySide6 6.11.2, Python 3.14).**
  `Test_model.STEP` (45 398 треугольников): одноразовая сборка топологии
  ~137 мс (в рабочем потоке, вместе с чтением модели); пересчёт силуэта
  `refreshTangents` ~2.3 мс/кадр против ~1.9-3.3 мс у аналитического контура
  (после фильтра силуэт - только гладкие горизонты, ~0.4-1.4 тыс. сегментов на
  ракурс). `Test_model_2.STEP`
  (1 028 треугольников): загрузка ~28 мс, пересчёт ~0.34 мс. В `GcodeViewer3D`
  пересчёт и так коалесцируется до одного раза на отрисованный кадр
  (`tangentsPending` + `FrameAnimation`), т.ч. стоимость ограничена кадром.
- **Удалён мёртвый слой `tangentGeometry`.** Легаси-геометрия касательных
  (`ToolpathGeometry`, сигнал `tangentChanged`, `_tan_geo`) не использовалась
  ни одним `.qml` (контур идёт через `hlrTangents`) и дублировала упаковку
  сегментов каждый кадр - удалена.
- **Проверки.** `test_tangent_policy.py` дополнен секцией меш-силуэта: на
  орбите контур замкнутого тела не пуст и стабилен (4.6-6.3 тыс. рёбер),
  концы силуэта не выходят из габарита меша, стенки шести крепёжных отверстий
  получают силуэт без аналитики; на `Test_model_2` силуэт несёт внешнее
  скругление R10 и не рисует линию на плоскости рядом с ним. `test_solid_skin.py`
  ждёт готовности модели (иначе появление кожи попадало в разницу) и мерит
  порог 10.5k под меш-силуэт. `test_ribbon_width.py`, `smoke_test_qml.py`,
  `py_compile`, offscreen `preview_3d.py` - зелёные.
- **Приёмка на `data/cad-testdata/Test_model_2.STEP`** (одно отверстие + четыре скругления
  R10): на ракурсах pitch=-22 yaw=44.2 dist=167.6 и pitch=-6.4 yaw=52.6
  «фантомной» линии у угла с отверстием нет, силуэт скругления не пропадает
  раньше края (стыковое ребро остаётся). Скриншоты - в `img/`
  (`mesh_sil_phantom_p22_y44.png`, `mesh_sil_boundary_p6_y53.png`, а также вид
  со стороны отверстия `mesh_sil_hole_*`).
- **Известные ограничения.** Силуэт рисуется только по гладким горизонтам;
  контур плоских острых кромок даёт слой статических B-rep рёбер. Силуэт
  гранится по тесселяции (на грубом меше видна огранка дуг); горизонт
  **вогнутых** переходов внутри карманов тоже рисуется (общий меш-силуэт, в
  отличие от «как SolidWorks»); модель `Test_model_2.STEP` - внешний
  диагностический образец и в дерево не добавляется (проверка по нему
  пропускается, если файла нет).

### 0.10.6 — 2026-10-15

- **Убран «фантом» у скругления рядом с отверстием.** Азимутальная маска
  покрытия скругления считалась по мешу кожи, и треугольники соседнего
  отверстия попадали в допуск `|r - R| < 0.25 мм`, добавляя лишние корзины:
  у скругления (65,40) в `Test_model_2` выходило 21 корзина (~118°) вместо 16
  (90°). Образующая рисовалась на ~28° дальше настоящей дуги, уходя на
  плоскость рядом с отверстием. Теперь маску по мешу **ограничиваем
  аналитической дугой грани STEP** (`s["arc"]`) - только у частичных дуг;
  полные отверстия (меш ~64 корзины) не режем, т.к. их полу-грани дают
  неверную 180-гр дугу.
- **Обрезка образующей - непрерывно по дуге.** Было сравнение с 64-корзинной
  маской: на границе дуги терялась до одной корзины (5.6°), и контур
  скругления гас раньше времени на скользящих углах. Теперь проверка
  `a0 .. a0+span` с допуском 2° (`_tangent_from_families`); диапазон дуги
  проброшен через семейства и склейку (`A0/A1`).
- Диагностика велась на отдельной простой модели `data/cad-testdata/Test_model_2.STEP`
  (одно отверстие + четыре скругления R10): прогон «только отверстия» и
  «только скругления» однозначно указал на скругление как источник фантома.

### 0.10.5 — 2026-10-15

- **Исправлен знак cam-float: линии уходили ЗА стенку.** В
  `HLRLineGeometry.set_segments` смещение считалось как `точка + ray/|ray|*d`,
  где `ray = точка - глаз` - то есть ОТ камеры. Пока кожа была `Blend`
  (глубину не писала), это не мешало; после сплошной `Opaque`-кожи (0.10.4)
  буфер глубины начал срезать уведённые назад линии - ближние кромки
  истоншались, а увеличение смещения только усиливало. Знак развёрнут
  (смещение К глазу), линии честно впереди поверхности. Замер: пикселей
  линии поверх кожи в solid 6616 -> 6878.
- **Вернул образующие выпуклых скруглений (внешний контур).** 0.10.4 гасил
  view-зависимые генераторы выпуклых галтелей целиком (по ориентации грани
  STEP) - вместе с ними пропадал и силуэт-контур скругления. Гейт снят:
  контур скругления снова рисуется аналитической образующей. Дубль
  (образующая рядом со стыковой кромкой) если и остаётся, то это силуэт И
  кромка, а не дубль.
- **Тангенциальные кромки не скрываем.** Пробовали скрывать стыки
  плоскость<->цилиндр «как SolidWorks» - фильтр рубил не только стыки
  скруглений R10, но и вертикальные рёбра галтелей R0.5-5 у кармана и
  отверстий («пропали почти все вертикальные линии»). Фильтр убран,
  статические рёбра снова 2426.
- **`CACHE_VER` 6 -> 8:** набор рёбер менялся, старый дисковый кэш модели
  отдавал прежние рёбра (фикс «не срабатывал» до очистки кэша).

### 0.10.4 — 2026-10-15

- **Сплошная кожа снова сплошная (просвечивающие грани серым в solid).**
  0.10.3 в описании обещал «кожу без альфа-блендинга», но материал был
  `alphaMode: Blend` с `opacity: 1.0`. Blend-материал идёт в прозрачную
  очередь и глубину не пишет, поэтому задние грани и скрытые рёбра
  просвечивали серым через тело. Теперь режимы разведены двумя моделями
  кожи: сплошная `PrincipledMaterial.Opaque` (пишет глубину, скрытое
  отсекается) и рентген `Blend` + `opacity 0.35`; переключает их тумблер X
  (смена `alphaMode` в рантайме материал не перекомпилирует - поэтому
  видимостью, а не свойством). Замер `test_solid_skin.py`: пикселей линии
  поверх кожи в solid 8907 против 10061 у прежней Blend-кожи.
- **Убрана «сдвоенная вертикаль» у скруглений (лишние грани в рентгене).**
  Правило «arc >= 85 гр» давало view-зависимую образующую выпуклому
  наружному скруглению R10. Вращаясь за камерой в 2-5 px от стыкового ребра
  скругления, она читалась сдвоенной вертикалью (замер pitch -10, yaw 210:
  генератор в x=382, стык в x=387). Вогнутость стенки определяется теперь по
  ориентации грани STEP (`BRep` REVERSED = вогнутая, отверстие; FORWARD =
  выпуклая галтель): генераторы остаются только у отверстий/расточек, контур
  скругления несут статические рёбра (дуга + два стыка). `orbit_counts`
  стал константой 52 вместо 52-55 - образующие больше не появляются и не
  исчезают на отдельных ракурсах. Проверка: `test_tangent_policy.py`
  (красна до фикса: «convex corner rounds tangented: 4»).
- **Исправлен cam-float статических рёбер.** `refreshTangents` передавал в
  `set_segments` упакованный буфер `_step_edges` (raw, nv, bounds) вместо
  координат; `np.asarray` падал на неоднородной форме, исключение глоталось
  `try/except`, и статические B-rep рёбра вообще не получали смещения к глазу
  (на скользящих видах их срезал буфер глубины). Теперь координаты

## Лёгкие оптимизации для Atom

Цель — снизить нагрузку на слабый CPU и встроенную графику, не ломая функциональность.

### Сделано ранее (для истории)
- Удалён `DirectionalLight`: все материалы сцены — `NoLighting` / `Unshaded`.
- Анимация инструмента переведена с `Timer` на `FrameAnimation`: множитель скорости не зависит от FPS, а шаг за кадр ограничен `0.1` с (`Math.min(frameTime, 0.1)`).
- Подписи осей перепроецируются по сигналам изменения камеры через `scheduleLabels()` / `Qt.callLater`, а не постоянным таймером 30 мс.

### Шаг 1. Скрытие «шкурки» STL и заготовки при вращении камеры — отменено
Пробовали скрывать полупрозрачную «шкурку» детали и заготовку (`#Cube`) на время вращения/зума камеры (свойство `interacting` + `Timer`-саттл). Отменено: при вращении сцены модель и контур заготовки пропадали, что неудобно. Скрытие и вся его обвязка (`interacting`, `interactSettleMs`, `settleTimer`, правки `MouseArea`) удалены. Из этого шага оставлен только `SceneEnvironment.antialiasingMode: SceneEnvironment.NoAA` (без MSAA на слабой встроенной графике).

### Шаг 2. Дисковый кэш подготовленных данных
`mock_backend.py`:
- Константы: `CACHE_VER = 1`, `CACHE_DIR = ~/.cache/gcode_viewer`, `CACHE_MAX_BYTES = 200 МБ`. `CNC_NO_CACHE=1` полностью отключает кэш; без numpy кэш не используется (путь расчёта как раньше).
- Кэш траектории — результат `_prepare_ordered()` в один `.npz` (`np.savez`, без pickle). Кэш контуров — результат `_feature_edges()` (ключ по STL).
- Ключ = `sha1(CACHE_VER | абспуть | размер | mtime_ns | _DECIMATE_TOL | _ARC_DECIMATE_TOL | тип)`.
- Используется только в фоновых потоках: `_worker_load` (путь) и `_compute_edges` (контуры); синхронные `load_string` / `load_gcode` кэш не используют. Запись атомарная (`os.replace`), повреждённый файл удаляется и пересчитывается, папка подрезается по `CACHE_MAX_BYTES` (удаляются самые старые по mtime).
- Замер на `data/cad-testdata/Test_model.ngc` + `Test_model.STL`: повторная загрузка (тёплый кэш) ~0.71 с → **~0.26 с**; счётчики и `sampleAt` идентичны холодному запуску и режиму `CNC_NO_CACHE=1`; повреждение `.npz` не приводит к ошибке.

### Шаг 3. Индексированный меш STL — не оставлен
Протестировано (`np.round(V*1000)` + `np.unique(axis=0)`) и **откачено**: на `Test_model.STL` 562 776 вершин → 93 774 уникальных (буфер 6.75 МБ → 1.13 МБ позиций + 2.25 МБ индексов), но дедупликация занимает ~0.26 с и попадает в критический путь до готовности меша. Время «до готовности меша» выросло: холодный запуск ~0.71 с → ~0.98 с (**+40 %**), тёплый ~0.26 с → ~0.55 с (**+98 %**). Превышен порог 25 % — шаг откачен полностью, в коде не оставлен.

### Рекомендации по запуску на Atom (проверять замером FPS на стойке, в коде не зашито)
- `QSG_RHI_BACKEND` — выбрать рабочий аппаратный бэкенд: `opengl`, `vulkan` или `d3d11` (на встроенной графике Intel обычно `d3d11`/`opengl`; замерить FPS каждого).
- `QSG_RENDER_LOOP` — попробовать `basic` (однопоточный) и `threaded` (по умолчанию); на слабом CPU и встроенной графике `basic` иногда стабильнее.
- Убедиться, что используется аппаратный GL, а не программный растеризатор (`llvmpipe`/Mesa softpipe) — программный GL на Atom резко просаживает FPS (проверять по логам Qt / драйвера).

## Исправленные баги

### Б1. «Пропала обводка контуров модели»
Контуры считаются в фоне, но геометрия обновлялась «на месте» после первого кадра — рендерер не перечитывал её.
**Фикс:** контуры публикуются **новым объектом геометрии** (`_set_edges_packed`), QML его подхватывает.

### Б2. «Цвета стали темнее»
Кастомный материал отдаёт цвет в линейном пространстве (в отличие от стандартных материалов), из-за чего зелёный `#1D9247` рисовался как `#034910`.
**Фикс:** в `toolpath.frag` добавлено кодирование linear→sRGB.
Проверка: зелёный `#1b9247`, синий `#1c6cb6`, пол `#c9ced4` — совпадают с заданными.

### Б3. «Пол уплыл в ноль координат»
`GridGeometry` не вызывал `update()` при перестроении, поэтому после загрузки (уже после первого кадра) сетка не перечитывалась и оставалась в начальной позиции.
**Фикс:** вызов `update()` в `GridGeometry._rebuild`.

### Б4. Контуры на numpy давали неверный результат
В `_feature_edges_np` массив граней строился как `np.repeat(np.arange(F), 3)`, хотя рёбра уложены тремя блоками `(a,b)|(b,c)|(c,a)` (слот `k` → грань `k % F`). Нужно `np.tile(..., 3)`. Из-за сдвига индексов грани спаривались неверно → почти все рёбра проходили порог (219k вместо 19k; на кубе 15 вместо 12).
**Фикс:** `np.tile`. Проверка: куб 12=12, деталь 18 986=18 986.

## Оптимизация загрузки

| Стадия | Было | Стало |
|---|---|---|
| Полная загрузка (УП+STL) | ~3.0 c | **~0.57 c** |
| Чтение STL | 0.22 c | 0.01 c (numpy) |
| Парсинг G-кода | 1.04 c | 0.29 c |
| Контуры (фоном) | 3.8 c | 0.69 c (numpy) |

Что сделано:
1. Парсер больше не строит дублирующие списки rapid/feed — только упорядоченный путь.
2. Упаковка вершин одним проходом через C-массив (`array`) / numpy.
3. Расчёт расстояний — inline / numpy `cumsum`.
4. Контуры вынесены в фоновый поток (модель видна до их готовности).
5. **numpy** (`2.5.3`, установлен через `pip`) используется опционально — с автоматическим фолбэком на чистый Python, если пакет недоступен.
6. Прореживание G1 (см. §2).

> Про параллелизм: узкое место — накладные расходы интерпретатора Python, а не арифметика, поэтому «ассемблерные вставки» не помогут. Тяжёлые операции уже выполняются в C (массивы, numpy) либо в отдельном потоке. `multiprocessing` на Windows даёт накладные на запуск процесса и сериализацию данных, сопоставимые с выигрышем.

## Асинхронная загрузка и numpy-упаковка (цель — Intel Atom)

Цель — не блокировать GUI-поток на слабом CPU и показывать траекторию до готовности STL.

1. **Загрузка вынесена в воркер-поток** (`GcodeToolpath.load_gcode_async`). Парсинг, построение буферов и чтение STL выполняются в фоновом потоке; на GUI-потоке остаётся только установка готовых данных (`set_packed`, `set_triangles`). Новые сигналы: `toolpathReady`, `meshReady`, `toolpathLoaded`, `loadFinished`, `loading` (`loadingChanged`). Токен загрузки (`_load_token`) отбрасывает устаревшие результаты. `preview_3d.py` показывает оверлей до `loadFinished`, без `QTimer`-хака.
2. **Траектория показывается раньше модели.** STL применяется отдельной фазой после УП, а не внутри общего `load_gcode`; контуры (feature edges) по-прежнему считаются фоном.
3. **Упаковка геометрии векторизована (numpy).** `_pack_stream_np` собирает оба потока (rapid/feed) за один проход над массивами; `_prepare_ordered` считает путь/центр/радиус/`min_y` тоже на массивах. `ToolpathGeometry` хранит готовые байты (`_raw`) и принимает их через `set_packed`, не пересобирая в Python. Фолбэк без numpy сохранён (`_pack_stream_py`).

Замер на `Сверление4.ngc` (108 288 сегментов) + `Сверление4.STL` (187 592 треугольника):

| Стадия | Было | Стало |
|---|---|---|
| Блокировка GUI-потока | ~0.82 c | **~0.001 c (путь) + ~0.036 c (меш)** |
| Готовность траектории | после STL | 0.47 c (в фоне) |
| Полная загрузка | 0.82 c | ~0.53 c |

Тяжёлая работа ушла в фон; окно остаётся отзывчивым (оверлей анимируется) даже на Atom.

## Дополнительно (анимация в C++, контуры, прореживание, слабый CPU)

4. **Анимация инструмента перенесена в C++.** QML больше не получает списки `moves/cumulative/moveRapid` (108k объектов) — вместо них слоты `GcodeToolpath.sampleAt(d)` и `isRapidAt(d)` с бинарным поиском (`np.searchsorted` / `bisect`). `GcodeViewer3D.qml` вызывает их напрямую; JS-функции `indexAt/sampleAt` и кэширующие свойства удалены.
5. **Контуры (feature edges):** `np.unique(q, axis=0)` считается один раз (был дважды), а результат упаковывается прямо в float32-буфер линий (`_pack_edges_np`) без промежуточного списка из 38k Python-кортежей и повторного прохода `update_geometry`.
6. **Прореживание дуг/циклов для превью.** Добавлен отдельный допуск `_ARC_DECIMATE_TOL` (по умолчанию 0.1 мм) — он убирает только суб-0.1-мм «дубли» тесселяции, не загрубляя окружности (обычный шаг точек дуги ≈0.2 мм сохраняется). Оба допуска настраиваются через env: `CNC_DECIMATE_TOL`, `CNC_ARC_DECIMATE_TOL`.
7. **Отсутствие numpy теперь заметно:** при импорте печатается предупреждение — на контроллере Atom numpy обязателен (fallback в разы медленнее).
8. **Метки осей** перепроецируются только при изменении входа (камера/размер), а не каждый кадр.

На `Сверление4.ngc`: точек пути 108 289 → **69 823** (−36%), feed-вершин 214 880 → **137 948**. Сэмплирование `sampleAt` совпадает с эталоном (расхождение — только float32 у `QVector3D`, как и у старого `Qt.vector3d`).

## Вьювер: скорость 1:1, режимы отображения, этапы

- **Автозапуск анимации убран.** При загрузке УП инструмент стоит в начале, весь путь нарисован; запуск — кнопкой «▶ Играть», клавишей `Пробел` или `P`.
- **Скорость 1:1 с реальной подачей.** `parse_gcode` хранит для каждого сегмента скорость (G1/G2/G3 — программная `F` мм/мин → мм/с, G0 — скорость быстрого хода, env `CNC_RAPID_SPEED_MMS`, дефолтная подача `CNC_DEFAULT_FEED_MMS`). Слот `GcodeToolpath.speedAt(d)` отдаёт скорость сегмента в точке пути; `speed` во вьювере — множитель воспроизведения (1.0 = реальное время), `↑/↓` меняют его.
- **Ограничение длины кода.** Режим «Ограничить длину» рисует только окно у инструмента и плавно растворяет дальние линии (шейдер `toolpath.frag`), дальние траектории появляются по мере выполнения. Переключатель «Весь код / Ограничить длину».
- **Этапы (блоки УП).** Границы операций берутся из тегов `(UI_TOOL: …)` (фолбэк — смена инструмента `T.. M6`). Парсер возвращает `stages` (нормированные диапазоны + метка), свойство `GcodeToolpath.stages`. Режим «По этапам» рисует только выбранный этап; кнопки `◀ ▶` и `PgUp/PgDn` переключают этапы, клавиша `T` — режим.
- **Кнопки режимов** (панель внизу): «Играть/Пауза», «Габарит заготовки» (`S`), «Модель детали» (`M`), «Весь код/Ограничить длину» (`L`), «По этапам» + переключение этапов.
- **Этапы = операции УП.** Раньше этапы делились по `UI_TOOL` (только смены инструмента → 4). Теперь операции берутся из маркеров: `UI_OP` (новый пост) → иначе `operation-comment` (по одной на секцию, стр. `onSection` в `linuxcnc_ui.cps`) → иначе `UI_TOOL`. Для `Test_model.ngc` распознаётся **13 операций** (`4, 5, 4, 2D-1, 2D-3, 4, 2D-1, 2D-2, 7, 8, 2D-2, 2D-6, 2D-7`), каждая с унаследованным инструментом (напр. `2D-1 · T1 фреза D4`). В пост `linuxcnc_ui.cps` добавлен вывод `(UI_OP: …)` на каждую секцию.
- **Переключатель этапов ◀ ▶ (`PgUp/PgDn`).** Режим «По этапам» **вкл** — как раньше: изолирует выбранную операцию и прыгает к её началу. Режим **выкл** — те же кнопки прокручивают **таймлайн** к границе соседней операции (без зацикливания, с упором в начало/конец УП); подпись этапа при этом следует за текущим положением инструмента.
- **Сверлильные циклы.** `_run_cycle` учитывает тип и поками: `G83` — покающее сверление с **полным выводом** между поками, `G73` — с частичным выводом (дробление стружки), `G81/G82` — прямой ход; учтён `Q` (глубина пока) и режим возврата `G98/G99`. Раньше сверло шло вниз одним ходом без вывода.
- **Анализ столкновений (фон).** После загрузки в отдельном потоке выполняется скан «оправка vs габарит заготовки»: по пути с шагом 1 мм ставятся цилиндры оправки (цанга r=8, корпус r=16 над вылетом) и проверяются на пересечение с AABB `UI_STOCK`. Результат — `GcodeToolpath.collisions` / `collisionCount` (объединённые диапазоны с точкой и глубиной проникновения). Во вьювере: красные маркеры в местах столкновения + индикатор «⚠ N столкн.» в панели (клик — переход к первому). Размеры оправки настраиваются env (`CNC_HOLDER_NUT_D/H`, `CNC_HOLDER_BODY_D/H`). Для `Test_model.ngc` найдено 12 задеваний сверлом T2 (~0.2 мм).
- **Инструмент по данным УП.** Каждый этап (`UI_TOOL`) несёт свой инструмент (`tool` в `stages`); вьювер по позиции/этапу вызывает `GcodeToolpath.setToolStage(i)` и перестраивает меш. Профиль резца теперь строится по `D`, `CR`, `TAPER/TIPA/TIPD`, `FL`, `SL`, `BL`, `SD`, `OL`: диаметр, форма кончика (flat/bull/ball/chamfer/drill) и **вылет** (видимая длина = body length `BL`, ограниченная `OL`, — так же, как показывает HSMWorks; хвостовик выше `BL` зажат в оправке) меняются вместе с инструментом.
- **Обводка.** Контур резца рисуется как **внешний силуэт** (inverted hull): профиль резца **раздувается наружу по нормалям** на постоянную величину `pad = max(0.12, 0.05·R)` (равномерная тонкая обводка, включая торец/кончик — смещение только по радиусу раньше оставляло вершину на месте и в конусе сверла давало «сходящиеся линии» из-за z-fighting). Увеличенная копия рисуется с отсечением ближней стороны (`cullMode: BackFaceCulling`, т.к. меш намотан внутрь), так что виден только тёмный кант — без колец, заливки и продольных образующих. Профиль исправлен для фрез с несколькими диаметрами: при `SD > D` теперь плоская ступенька на плече, а не наклонный конус. У обводок цилиндров шпинделя (`WireCylinderGeometry`) убраны 4 вертикальные «силуэтные» линии: боковая поверхность непрерывна, и эти линии читались как ложные вертикальные швы на гранях. Остались только верхнее/нижнее кольца.
- **Оправка (ER20).** Шпиндель заменён на примитивную модель **ER20-гайки + корпуса** (тело вращения из бэкенда, `holderGeometry`), низ оправки — на вылете инструмента. Размеры: env `CNC_HOLDER_NUT_D/H` (33/22), `CNC_HOLDER_BODY_D/H` (46/50). Вылет можно брать из УП: пост выводит `(UI_HOLDER: GAUGE=..)` (HSMWorks/Fusion: `operation:tool_holderGaugeLength`), вьювер парсит `GcodeToolpath.holderGauge` и ставит оправку по фактическому вылету (иначе — по `BL`).
- **Обводка = силуэт + кольца (тонко).** Вертикальный контур — силуэт (inverted hull), масштабируется **радиально** по дистанции камеры, чтобы держать ~`outlinePx` (1 px) при любом зуме (раньше в мировых единицах был суб-пиксельным). Горизонтальные рёбра — отдельная линейная геометрия `toolRings` / `holderRings` (кольца только по реальным рёбрам профиля, `_profile_ring_points`, порог 20°, чтобы сферы не превращались в «клетку»). Для оправки силуэт — по **открытой оболочке** (без плоских торцов-крышек), чтобы увеличенная копия не давала тёмных «стаканов».
- **Обводка детали (STL).** Силуэт (inverted hull) для детали **не подошёл**: «кожа» полупрозрачная и не перекрывает дальнюю сторону увеличенной копии — модель заливалась чёрным, поэтому силуэт убран, а цвет детали возвращён к исходному (`#F6E7A1`, opacity 0.35). Обводка — **рёбра** (`partEdges`, `#C2701F`): теперь прозрачным материалом, чтобы рисоваться в transparent-проходе **после** «кожи» и быть заметнее (у детали 6088 вертикальных рёбер из 18986).
- **Проверка инструмента (заготовка).** `_tool_check_report` сравнивает каждый инструмент УП с таблицей стойки: совпадение номера, измеренный вылет (length offset) vs заданный в УП (`OL`) — **короче нельзя** (опасно), длиннее допустимо, если не выходим за лимит оси Z. API (для будущей стыковки с интерфейсом): `setMachineTools([{number,length,name,enabled}])`, `setMachineLimits({zMax,zMin})`, `runToolCheck()`, свойства `toolCheck` / `toolIssueCount`. Во вьювере — оранжевый индикатор «⚠ Инструмент: N». Пока таблица стойки не подключена — проверка пустая (без ложных срабатываний).

## Примечания / ограничения

- numpy-путь контуров включён с фолбэком на Python (`_feature_edges_py`) на случай исключения.
- Скрытие пройденных линий использует `discard` в кастомном материале; точка сброса — `Esc`.
- Тег `UI_STOCK` в УП влияет на положение и размеры заготовки и пола; без него пол привязывается к траектории.
- Тег `UI_TOOL` в УП задаёт форму инструмента во вьювере (`toolGeometry`), а `UI_CAD_MATRIX` — трансформу CAD-модели.

## Возможные улучшения (бэклог)

Переход на меш-силуэт (`0.11.0`) убрал слой эвристик аналитического контура,
но у него есть известные компромиссы. Если вернёмся к теме — направления:

1. **Дефасетизация силуэта.** Сейчас силуэт гранится по тесселяции (огранка дуг
   на грубом меше). Идеи: подгонять силуэтные полилинии к аналитическим кривым
   (продолжения/сглаживание цепочек рёбер), либо собирать «горизонт» из
   связанных цепочек с субпиксельной выборкой нормалей.
2. **Фильтр горизонта по типу перехода.** Общий меш-силуэт рисует и **вогнутые**
   горизонты внутри карманов (в отличие от SolidWorks, где термин «silhouette»
   применяется к выпуклым/внешним). Вариант: помечать переходы как выпуклые/
   вогнутые по знаку `n1 x n2` и не рисовать вогнутые внутри карманов.
3. **Точный HLR из OCCT** (`HLRBRep_Algo` / `HLRBRep_PolyAlgo` +
   `HLRAlgo_Projector`) на «успокоившемся» ракурсе, асинхронно, с кэшем по углу:
   даёт точные видимые/скрытые кривые любой формы без огранки. Дороже
   (десятки–сотни мс на пересчёт) — поэтому не покадрово, а по settle.
4. **Асинхронность/троттлинг пересчёта** при больших мешах: вынести
   `_mesh_silhouette_segments` в рабочий поток и/или коалесцировать чаще
   (сейчас — один раз на отрисованный кадр).
5. **Отсечение скрытого в рентгене.** В `X`-режиме кожа `Blend` глубину не
   пишет, силуэт виден целиком («показать всё»). При желании — отдельный
   depth-prepass или CPU-zbuffer, чтобы скрытые участки силуэта гасли и в X.

Связанные файлы: `modules/gcode-viewer/mock_backend.py`
(`_build_silhouette_topology`, `_mesh_silhouette_segments`),
`stepledges.vert/.frag`, флаг `CNC_SILHOUETTE=mesh|analytic`.
